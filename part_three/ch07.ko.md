# Comonad

monad를 다루었으니 이제 쌍대성의 혜택을 거두어 화살표를 뒤집고 반대 범주에서 작업하기만 하면 comonad를 공짜로 얻을 수 있다.

가장 기본적인 수준에서 monad는 다음 Kleisli 화살표의 합성에 관한 것임을 기억하자.

<pre>a -> m b</pre>

여기서 `m`은 monad인 functor다. comonad에는 뒤집힌 `m`처럼 보이는 문자 `w`를 사용하고 co-Kleisli 화살표를 다음 타입의 사상으로 정의할 수 있다.

<pre>w a -> b</pre>

co-Kleisli 화살표의 물고기 연산자에 해당하는 것은 다음과 같다.

<pre>(=>=) :: (w a -> b) -> (w b -> c) -> (w a -> c)</pre>

co-Kleisli 화살표가 범주를 이루려면 `extract`라고 하는 항등 co-Kleisli 화살표도 있어야 한다.

<pre>extract :: w a -> a</pre>

`return`의 쌍대다. 결합법칙과 왼쪽·오른쪽 항등 법칙도 부과해야 한다. 모두 합치면 하스켈에서 comonad를 다음처럼 정의할 수 있다.

<pre>class Functor w => Comonad w where
    (=>=) :: (w a -> b) -> (w b -> c) -> (w a -> c)
    extract :: w a -> a</pre>

실제로는 곧 보게 될 조금 다른 원시 연산을 사용한다.

그렇다면 프로그래밍에서 comonad는 어디에 쓸까?

## Comonad로 프로그래밍하기

monad와 comonad를 비교하자. monad는 `return`을 사용해 값을 컨테이너에 넣는 방법을 제공하지만 안에 저장된 값에는 접근하게 해 주지 않는다. 물론 monad를 구현하는 데이터 구조가 내용물 접근을 제공할 수도 있지만 이는 덤으로 여긴다. monad에서 값을 꺼내는 공통 인터페이스는 없다. 내용물을 절대로 노출하지 않는 것을 자랑으로 삼는 `IO` monad도 보았다.

반면 comonad는 값 하나를 꺼내는 수단을 제공하지만 값을 넣는 수단은 제공하지 않는다. comonad를 컨테이너로 생각한다면 언제나 내용물이 미리 채워져 있고 안을 들여다볼 수 있다.

Kleisli 화살표가 값을 받아 문맥으로 장식한 결과를 만드는 것처럼 co-Kleisli 화살표는 값과 그 전체 문맥을 받아 결과를 만든다. _문맥적 계산_을 구현한 것이다.

## 곱 Comonad

reader monad를 기억하는가? 읽기 전용 환경 `e`에 접근해야 하는 계산을 구현하는 문제를 해결하려고 도입했다. 그런 계산은 다음 형태의 순수 함수로 나타낼 수 있다.

<pre>(a, e) -> b</pre>

커링을 사용해 Kleisli 화살표로 바꾸었다.

<pre>a -> (e -> b)</pre>

하지만 이 함수들은 이미 co-Kleisli 화살표 형태를 가진다. 인자를 더 편리한 functor 형태로 다듬자.

<pre>data Product e a = P e a
  deriving Functor</pre>

합성하는 화살표들이 같은 환경을 사용하게 해 합성 연산자를 쉽게 정의할 수 있다.

<pre>(=>=) :: (Product e a -> b) -> (Product e b -> c) -> (Product e a -> c)
f =>= g = \(P e a) -> let b = f (P e a)
                          c = g (P e b)
                       in c</pre>

`extract` 구현은 환경을 무시할 뿐이다.

<pre>extract (P e a) = a</pre>

놀랍지 않게 곱 comonad는 reader monad와 정확히 같은 계산을 수행할 수 있다. 어떤 면에서는 환경의 comonad 구현이 "문맥 속 계산"이라는 정신을 따르므로 더 자연스럽다. 한편 monad에는 `do` 표기법이라는 편리한 문법 설탕이 있다.

reader monad와 곱 comonad의 연결은 더 깊으며 reader functor가 곱 functor의 오른쪽 수반이라는 사실과 관련 있다. 하지만 일반적으로 comonad는 monad와 다른 계산 개념을 다룬다. 나중에 더 많은 예를 보겠다.

`Product` comonad는 튜플과 레코드를 비롯한 임의의 곱 타입으로 쉽게 일반화할 수 있다.

## 합성 해부하기

쌍대화 과정을 계속해 monad의 bind와 join을 쌍대화할 수도 있다. 또는 물고기 연산자의 구조를 연구했던 monad의 과정을 반복할 수 있다. 후자가 더 많은 통찰을 준다.

출발점은 합성 연산자가 `w a`를 받아 `c`를 만드는 co-Kleisli 화살표를 만들어야 한다는 사실이다. `c`를 만드는 유일한 방법은 두 번째 함수를 타입 `w b`의 인자에 적용하는 것이다.

<pre>(=>=) :: (w a -> b) -> (w b -> c) -> (w a -> c)
f =>= g = g ... </pre>

하지만 `g`에 줄 타입 `w b`의 값을 어떻게 만들까? 타입 `w a`의 인자와 함수 `f :: w a -> b`가 있다. 해법은 bind의 쌍대인 `extend`를 정의하는 것이다.

<pre>extend :: (w a -> b) -> w a -> w b</pre>

`extend`로 합성을 구현할 수 있다.

<pre>f =>= g = g . extend f</pre>

`extend`도 해부할 수 있을까? 함수 `w a -> b`를 인자 `w a`에 적용하면 된다고 생각할 수 있지만, 그러면 결과 `b`를 `w b`로 바꿀 방법이 없음을 곧 깨닫는다. comonad는 값을 끌어올리는 수단을 제공하지 않는다. monad의 비슷한 구성에서는 이 지점에서 `fmap`을 사용했다. 여기서 `fmap`을 사용하려면 타입 `w (w a)`가 있어야 한다. `w a`를 `w (w a)`로 바꿀 수만 있다면 된다. 마침 이것이 정확히 `join`의 쌍대이며 `duplicate`라고 부른다.

<pre>duplicate :: w a -> w (w a)</pre>

따라서 monad와 마찬가지로 co-Kleisli 화살표, `extend`, `duplicate`를 사용한 comonad의 동등한 정의가 셋 있다. 다음은 `Control.Comonad` 라이브러리에서 그대로 가져온 하스켈 정의다.

<pre>class Functor w => Comonad w where
  extract :: w a -> a
  duplicate :: w a -> w (w a)
  duplicate = extend id
  extend :: (w a -> b) -> w a -> w b
  extend f = fmap f . duplicate</pre>

`duplicate`로 표현한 `extend`의 기본 구현과 그 역이 제공되므로 둘 중 하나만 재정의하면 된다.

이 함수들의 직관은 일반적으로 comonad를 타입 `a`의 값으로 채워진 컨테이너로 생각하는 데서 나온다. 곱 comonad는 값 하나뿐인 특별한 경우였다. `extract`로 쉽게 접근할 수 있는 "현재" 값이라는 개념이 있다. co-Kleisli 화살표는 현재 값에 초점을 맞춘 계산을 수행하지만 주변 값 모두에 접근할 수 있다. Conway의 생명 게임을 생각해 보라. 각 셀은 보통 `True`나 `False`인 값을 담는다. 생명 게임에 대응하는 comonad는 "현재" 셀에 초점을 맞춘 셀 격자일 것이다.

그렇다면 `duplicate`는 무엇을 할까? comonad 컨테이너 `w a`를 받아 컨테이너들의 컨테이너 `w (w a)`를 만든다. 각 컨테이너는 `w a` 안의 서로 다른 `a`에 초점을 맞춘다. 생명 게임에서는 격자의 격자를 얻으며 바깥 격자의 각 셀은 서로 다른 셀에 초점을 맞춘 안쪽 격자를 담는다.

이제 `extend`를 보자. co-Kleisli 화살표와 `a`로 채워진 comonad 컨테이너 `w a`를 받아 계산을 모든 `a`에 적용하고 `b`로 바꾼다. 결과는 `b`로 채워진 comonad 컨테이너다. `extend`는 초점을 한 `a`에서 다음 `a`로 옮기며 각각에 co-Kleisli 화살표를 적용한다. 생명 게임의 co-Kleisli 화살표는 현재 셀의 새 상태를 계산하며 그 문맥인 가까운 이웃을 볼 것이다. `extend`의 기본 구현이 이 과정을 보여 준다. 먼저 `duplicate`를 호출해 가능한 모든 초점을 만들고 각각에 `f`를 적용한다.

## Stream Comonad

컨테이너의 한 원소에서 다른 원소로 초점을 옮기는 과정은 무한 stream의 예에서 가장 잘 보인다. 빈 생성자가 없다는 점을 제외하면 리스트와 같다.

<pre>data Stream a = Cons a (Stream a)</pre>

자명하게 `Functor`다.

<pre>instance Functor Stream where
    fmap f (Cons a as) = Cons (f a) (fmap f as)</pre>

stream의 초점은 첫 번째 원소이므로 `extract` 구현은 다음과 같다.

<pre>extract (Cons a _) = a</pre>

`duplicate`는 각각 다른 원소에 초점을 맞춘 stream들의 stream을 만든다.

<pre>duplicate (Cons a as) = Cons (Cons a as) (duplicate as)</pre>

첫 번째 원소는 원래 stream, 두 번째는 원래 stream의 꼬리, 세 번째는 그 꼬리의 꼬리이며 무한히 계속된다.

전체 인스턴스는 다음과 같다.

<pre>instance Comonad Stream where
    extract (Cons a _) = a
    duplicate (Cons a as) = Cons (Cons a as) (duplicate as)</pre>

stream을 보는 매우 함수형인 방법이다. 명령형 언어에서는 아마 stream을 한 위치 옮기는 메서드 `advance`로 시작했을 것이다. 여기서 `duplicate`는 이동된 모든 stream을 한 번에 만든다. 하스켈의 지연성이 이를 가능하게 하며 바람직하게까지 만든다. 물론 실용적인 `Stream`을 만들려면 `advance`에 해당하는 것도 구현할 것이다.

<pre>tail :: Stream a -> Stream a
tail (Cons a as) = as</pre>

하지만 comonad 인터페이스의 일부는 아니다.

디지털 신호 처리 경험이 있다면 stream의 co-Kleisli 화살표가 디지털 필터일 뿐이며 `extend`가 필터링된 stream을 만든다는 사실을 바로 알 것이다.

간단한 예로 이동 평균 필터를 구현하자. 다음은 stream의 원소 `n`개를 더하는 함수다.

```
sumS :: Num a => Int -> Stream a -> a
sumS n (Cons a as) = if n <= 0 then 0 else a + sumS (n - 1) as
```

stream의 처음 `n`개 원소 평균을 계산하는 함수는 다음과 같다.

<pre>average :: Fractional a => Int -> Stream a -> a
average n stm = (sumS n stm) / (fromIntegral n)</pre>

부분 적용된 `average n`은 co-Kleisli 화살표이므로 stream 전체에 `extend`할 수 있다.

<pre>movingAvg :: Fractional a => Int -> Stream a -> Stream a
movingAvg n = extend (average n)</pre>

결과는 이동 평균의 stream이다.

stream은 단방향 1차원 comonad의 예다. 양방향으로 만들거나 2차원 이상으로 쉽게 확장할 수 있다.

## 범주론적으로 본 Comonad

범주론에서 comonad를 정의하는 것은 쌍대성의 간단한 연습이다. monad와 마찬가지로 endofunctor `T`에서 시작한다. monad를 정의하는 두 자연 변환 η와 μ의 방향을 comonad에서는 뒤집기만 한다.

<pre>ε :: T -> I
δ :: T -> T<sup>2</sup></pre>

이 변환의 성분은 `extract`와 `duplicate`에 대응한다. comonad 법칙은 monad 법칙의 거울상이다. 놀랄 것은 없다.

수반에서 monad를 유도한 것도 있다. 쌍대성은 수반을 뒤집어 왼쪽 수반이 오른쪽이 되고 그 역도 성립한다. 합성 `R ∘ L`이 monad를 정의하므로 `L ∘ R`은 comonad를 정의해야 한다. 수반의 쌍대단위:

<pre>ε :: L ∘ R -> I</pre>

는 실제로 comonad 정의에서 보는 ε, 성분으로는 하스켈의 `extract`와 같다. 수반의 단위:

<pre>η :: I -> R ∘ L</pre>

를 사용해 `L ∘ R` 가운데에 `R ∘ L`을 넣어 `L ∘ R ∘ L ∘ R`을 만들 수 있다. `T`에서 T<sup>2</sup>을 만드는 것이 δ를 정의하며 이것으로 comonad 정의가 완성된다.

monad가 모노이드라는 것도 보았다. 이 명제의 쌍대에는 comonoid가 필요한데 comonoid란 무엇일까? 한 객체 범주로서의 원래 모노이드 정의를 쌍대화해도 흥미로운 것이 나오지 않는다. 모든 endomorphism의 방향을 뒤집으면 또 다른 모노이드를 얻는다. 하지만 monad를 다룰 때 모노이드 범주의 객체라는 더 일반적인 모노이드 정의를 사용했음을 기억하자. 구성은 두 사상을 바탕으로 했다.

<pre>μ :: m ⊗ m -> m
η :: i -> m</pre>

이 사상들을 뒤집으면 모노이드 범주의 comonoid를 얻는다.

<pre>δ :: m -> m ⊗ m
ε :: m -> i</pre>

하스켈로 comonoid 정의를 쓸 수 있다.

<pre>class Comonoid m where
  split   :: m -> (m, m)
  destroy :: m -> ()</pre>

하지만 상당히 자명하다. `destroy`는 인자를 무시한다.

<pre>destroy _ = ()</pre>

`split`은 함수의 쌍일 뿐이다.

<pre>split x = (f x, g x)</pre>

이제 모노이드의 단위 법칙과 쌍대인 comonoid 법칙을 생각하자.

<pre>lambda . bimap destroy id . split = id
rho . bimap id destroy . split = id</pre>

여기서 `lambda`와 `rho`는 각각 왼쪽과 오른쪽 unitor다. [모노이드 범주](#monad-categorically)의 정의를 보라. 정의를 대입하면 다음을 얻는다.

<pre>lambda (bimap destroy id (split x))
= lambda (bimap destroy id (f x, g x))
= lambda ((), g x)
= g x</pre>

따라서 `g = id`임을 증명한다. 마찬가지로 두 번째 법칙을 전개하면 `f = id`다. 결론은 다음과 같다.

<pre>split x = (x, x)</pre>

하스켈, 더 일반적으로 **Set** 범주의 모든 객체는 자명한 comonoid임을 보여 준다.

다행히 comonoid를 정의할 더 흥미로운 모노이드 범주가 있다. 그중 하나가 endofunctor의 범주다. monad가 endofunctor 범주의 모노이드인 것처럼:

comonad는 endofunctor 범주의 comonoid다.

## Store Comonad

comonad의 또 다른 중요한 예는 state monad의 쌍대다. costate comonad 또는 store comonad라고 한다.

state monad는 지수를 정의하는 수반이 만든다는 것을 앞에서 보았다.

<pre>L z = z × s
R a = s ⇒ a</pre>

같은 수반으로 costate comonad를 정의하겠다. comonad는 합성 `L ∘ R`로 정의한다.

<pre>L (R a) = (s ⇒ a) × s</pre>

하스켈로 옮기면 왼쪽의 `Prod` functor와 오른쪽의 `Reader` functor 사이 수반에서 시작한다. `Reader` 뒤에 `Prod`를 합성하면 다음 정의와 동등하다.

<pre>data Store s a = Store (s -> a) s</pre>

객체 `a`에서 취한 수반의 쌍대단위는 다음 사상이다.

<pre>ε<sub>a</sub> :: ((s ⇒ a) × s) -> a</pre>

하스켈 표기로는:

<pre>counit (Prod (Reader f, s)) = f s</pre>

우리의 `extract`가 된다.

<pre>extract (Store f s) = f s</pre>

수반의 단위:

<pre>unit a = Reader (\s -> Prod (a, s))</pre>

는 부분 적용된 데이터 생성자로 다시 쓸 수 있다.

<pre>Store f :: s -> Store f s</pre>

δ, 즉 `duplicate`를 다음 수평 합성으로 구성한다.

<pre>δ :: L ∘ R -> L ∘ R ∘ L ∘ R
δ = L ∘ η ∘ R</pre>

η를 가장 왼쪽의 `L`, 즉 `Prod` functor를 가로질러 넣어야 한다. 쌍의 왼쪽 성분에 η, 즉 `Store f`를 적용한다는 뜻이다. `Prod`의 `fmap`이 그렇게 할 것이다. 다음을 얻는다.

<pre>duplicate (Store f s) = Store (Store f) s</pre>

δ 공식에서 `L`과 `R`은 성분이 항등 사상인 항등 자연 변환을 나타낸다는 것을 기억하자.

`Store` comonad의 전체 정의는 다음과 같다.

<pre>instance Comonad (Store s) where
  extract (Store f s) = f s
  duplicate (Store f s) = Store (Store f) s</pre>

`Store`의 `Reader` 부분을 타입 `s`의 원소를 키로 하는 `a`의 일반화된 컨테이너로 생각할 수 있다. 예를 들어 `s`가 `Int`이면 `Reader Int a`는 `a`의 무한 양방향 stream이다. `Store`는 이 컨테이너를 키 타입의 값과 짝짓는다. 이 경우 `Reader Int a`는 `Int`와 짝지어진다. `extract`는 이 정수로 무한 stream을 인덱싱한다. `Store`의 두 번째 성분을 현재 위치로 생각할 수 있다.

이 예에서 `duplicate`는 `Int`로 인덱싱한 새 무한 stream을 만든다. 이 stream은 원소로 stream을 담는다. 특히 현재 위치에는 원래 stream이 있다. 하지만 양수나 음수인 다른 `Int`를 키로 사용하면 새 인덱스에 위치하도록 이동된 stream을 얻는다.

일반적으로 `duplicate`된 `Store`에 `extract`를 적용하면 원래 `Store`를 만든다는 것을 확인할 수 있다. 실제로 comonad의 항등 법칙은 `extract . duplicate = id`라고 말한다.

`Store` comonad는 `Lens` 라이브러리의 이론적 기반으로 중요한 역할을 한다. 개념적으로 `Store s a` comonad는 타입 `s`를 인덱스로 사용해 데이터 타입 `a`의 특정 하위 구조에 렌즈처럼 "초점을 맞추는" 발상을 캡슐화한다. 특히 다음 타입의 함수:

<pre>a -> Store s a</pre>

는 함수 쌍과 동등하다.

<pre>set :: a -> s -> a
get :: a -> s</pre>

`a`가 곱 타입이면 `set`은 `a` 안의 타입 `s` 필드를 설정하고 수정된 `a`를 반환하도록 구현할 수 있다. 마찬가지로 `get`은 `a`에서 `s` 필드의 값을 읽도록 구현할 수 있다. 다음 절에서 이 발상을 더 탐구하겠다.
