# Monad: 프로그래머의 정의 {#monads-programmers-definition}

프로그래머들은 monad를 둘러싼 신화 체계 전체를 발전시켰다. 프로그래밍에서 가장 추상적이고 어려운 개념 중 하나라고 한다. 이를 "깨달은" 사람과 그렇지 못한 사람이 있다. 많은 이에게 monad를 이해하는 순간은 신비 체험과 같다. monad는 매우 다양한 구성의 본질을 추상화하므로 일상생활에서 좋은 비유를 찾기 어렵다. 코끼리의 서로 다른 부분을 만지고 "밧줄이다", "나무줄기다", "부리토다!"라고 의기양양하게 외치는 장님들처럼 어둠 속을 더듬을 수밖에 없다.

분명히 해 두자. monad를 둘러싼 신비주의는 모두 오해의 결과다. monad는 매우 단순한 개념이다. 혼란을 일으키는 것은 monad 응용의 다양성이다.

이 글을 조사하면서 덕트 테이프와 그 용도를 찾아보았다. 할 수 있는 일의 일부는 다음과 같다.

* 덕트 밀봉
* Apollo 13의 CO<sub>2</sub> 정화 장치 수리
* 사마귀 치료
* Apple iPhone 4의 통화 끊김 문제 해결
* 무도회 드레스 만들기
* 현수교 건설

덕트 테이프가 무엇인지 모른 채 이 목록만 보고 알아내려 한다고 상상해 보라. 행운을 빈다!

그래서 "monad는 ...와 같다"는 진부한 비유 모음에 하나를 더하고 싶다. monad는 덕트 테이프와 같다. 응용은 매우 다양하지만 원리는 아주 단순하다. 대상을 서로 붙인다. 더 정확히는 대상을 합성한다.

이는 특히 명령형 배경에서 온 많은 프로그래머가 monad를 이해하기 어려워하는 이유를 일부 설명한다. 프로그램을 함수 합성으로 생각하는 데 익숙하지 않기 때문이다. 이해할 만하다. 중간 값을 함수에서 함수로 직접 넘기기보다 이름을 붙이는 일이 많다. 짧은 접착 코드 조각을 도우미 함수로 추상화하지 않고 인라인으로 넣기도 한다. 다음은 C로 쓴 명령형 벡터 길이 함수다.

<pre>double vlen(double * v) {
  double d = 0.0;
  int n;
  for (n = 0; n < 3; ++n)
    d += v[n] * v[n];
  return sqrt(d);
}</pre>

함수 합성을 명시한 양식화된 하스켈 버전과 비교해 보자.

<pre>vlen = sqrt . sum . fmap  (flip (^) 2)</pre>

더 난해하게 만들려고 지수 연산자 `(^)`의 두 번째 인자를 `2`로 설정해 부분 적용했다.

하스켈의 point-free 스타일이 언제나 낫다는 주장은 아니다. 다만 프로그래밍에서 하는 모든 일의 밑바닥에는 함수 합성이 있다. 실제로 함수를 합성하면서도 하스켈은 monad 합성을 위한 `do` 표기법이라는 명령형 스타일의 문법을 제공하려고 많은 노력을 기울인다. 나중에 사용법을 보겠다. 먼저 monad 합성이 애초에 왜 필요한지 설명하겠다.

## Kleisli 범주

앞서 일반 함수에 장식을 더해 [writer monad](#kleisli-categories)에 도달했다. 반환 값을 문자열, 더 일반적으로는 모노이드의 원소와 짝짓는 장식이었다. 이제 이 장식이 functor임을 알아볼 수 있다.

<pre>newtype Writer w a = Writer (a, w)

instance Functor (Writer w) where
  fmap f (Writer (a, w)) = Writer (f a, w)</pre>

이어서 다음 형태의 함수인 장식된 함수, 즉 Kleisli 화살표를 합성하는 방법을 찾았다.

<pre>a -> Writer w b</pre>

로그 축적은 합성 내부에 구현했다.

이제 Kleisli 범주를 더 일반적으로 정의할 준비가 되었다. 범주 *C*와 endofunctor `m`으로 시작한다. 대응하는 Kleisli 범주 *K*는 *C*와 객체가 같지만 사상은 다르다. *K*의 객체 `a`, `b` 사이 사상은 원래 범주 *C*에서 다음 사상으로 구현한다.

<pre>a -> m b</pre>

*K*의 Kleisli 화살표를 `a`와 `m b` 사이가 아니라 `a`와 `b` 사이의 사상으로 취급한다는 점을 기억해야 한다.

앞의 예에서 `m`은 어떤 고정된 모노이드 `w`에 대한 `Writer w`였다.

Kleisli 화살표는 적절한 합성을 정의할 수 있을 때만 범주를 이룬다. 결합법칙을 만족하며 모든 객체에 항등 화살표가 있는 합성이 존재하면 functor `m`을 *monad*라고 하고 그 결과 범주를 Kleisli 범주라고 한다.

하스켈에서 Kleisli 합성은 물고기 연산자 `>=>`로 정의하고 항등 화살표는 `return`이라는 다형 함수다. Kleisli 합성을 사용한 monad 정의는 다음과 같다.

<pre>class Monad m where
  (>=>) :: (a -> m b) -> (b -> m c) -> (a -> m c)
  return :: a -> m a</pre>

monad를 정의하는 동등한 방법은 많으며 이것은 하스켈 생태계의 주된 정의가 아님을 기억하자. 개념적으로 단순하고 직관을 주어 좋아하지만 프로그래밍에는 더 편리한 다른 정의가 있다. 곧 이야기하겠다.

이 표현에서는 monad 법칙을 아주 쉽게 쓸 수 있다. 하스켈이 강제할 수는 없지만 방정식 추론에 사용할 수 있다. Kleisli 범주의 표준 합성 법칙일 뿐이다.

<pre>(f >=> g) >=> h = f >=> (g >=> h) -- 결합법칙
return >=> f = f                  -- 왼쪽 단위
f >=> return = f                  -- 오른쪽 단위</pre>

이 정의는 monad가 실제로 무엇인지도 표현한다. 장식된 함수를 합성하는 방법이다. 부수 효과나 상태에 관한 것이 아니라 합성에 관한 것이다. 나중에 장식된 함수로 여러 효과나 상태를 표현할 수 있음을 보겠지만 그것이 monad의 목적은 아니다. monad는 한 장식된 함수의 끝을 다른 장식된 함수의 끝에 붙이는 끈끈한 덕트 테이프다.

`Writer` 예로 돌아가면 로깅 함수, 즉 `Writer` functor의 Kleisli 화살표는 `Writer`가 monad이므로 범주를 이룬다.

<pre>instance Monoid w => Monad (Writer w) where
    f >=> g = \a ->
        let Writer (b, s)  = f a
            Writer (c, s') = g b
        in Writer (c, s `mappend` s')
    return a = Writer (a, mempty)</pre>

`w`의 모노이드 법칙이 만족되면 `Writer w`의 monad 법칙도 만족된다. 모노이드 법칙 역시 하스켈이 강제할 수 없다.

`Writer` monad에는 `tell`이라는 유용한 Kleisli 화살표가 있다. 인자를 로그에 추가하는 것이 유일한 목적이다.

<pre>tell :: w -> Writer w ()
tell s = Writer ((), s)</pre>

나중에 다른 monad 함수의 구성 요소로 사용하겠다.

## 물고기 해부

서로 다른 monad의 물고기 연산자를 구현하다 보면 많은 코드가 반복되어 쉽게 분리할 수 있음을 곧 깨닫는다. 우선 두 함수의 Kleisli 합성은 함수를 반환해야 하므로 구현은 타입 `a`의 인자를 받는 람다로 시작할 수 있다.

<pre>(>=>) :: (a -> m b) -> (b -> m c) -> (a -> m c)
f >=> g = \a -> ...</pre>

이 인자로 할 수 있는 유일한 일은 `f`에 전달하는 것이다.

<pre>f >=> g = \a -> let mb = f a
                in ...</pre>

이제 타입 `m b`의 객체와 함수 `g :: b -> m c`를 가지고 타입 `m c`의 결과를 만들어야 한다. 그 일을 하는 함수를 정의하자. bind라고 하며 보통 중위 연산자로 쓴다.

<pre>(>>=) :: m a -> (a -> m b) -> m b</pre>

모든 monad에 대해 물고기 연산자 대신 bind를 정의할 수 있다. 실제로 하스켈의 표준 monad 정의는 bind를 사용한다.

<pre>class Monad m where
    (>>=) :: m a -> (a -> m b) -> m b
    return :: a -> m a</pre>

`Writer` monad의 bind 정의는 다음과 같다.

<pre>(Writer (a, w)) >>= f = let Writer (b, w') = f a
                        in  Writer (b, w `mappend` w')</pre>

물고기 연산자 정의보다 실제로 짧다.

`m`이 functor라는 사실을 이용해 bind를 더 해부할 수 있다. `fmap`으로 함수 `a -> m b`를 `m a`의 내용물에 적용하면 `a`가 `m b`로 바뀐다. 따라서 적용 결과의 타입은 `m (m b)`다. 원하는 `m b`는 아니지만 거의 다 왔다. `m`의 이중 적용을 붕괴시키거나 평평하게 만드는 함수만 있으면 된다. 이를 `join`이라고 한다.

<pre>join :: m (m a) -> m a</pre>

`join`을 사용해 bind를 다시 쓸 수 있다.

<pre>ma >>= f = join (fmap f ma)</pre>

그러면 monad를 정의하는 세 번째 방법을 얻는다.

<pre>class Functor m => Monad m where
    join :: m (m a) -> m a
    return :: a -> m a</pre>

여기서는 `m`이 `Functor`일 것을 명시적으로 요구했다. 앞의 두 정의에서는 그럴 필요가 없었다. 물고기 또는 bind 연산자를 지원하는 모든 타입 생성자 `m`은 자동으로 functor이기 때문이다. 예를 들어 bind와 `return`으로 `fmap`을 정의할 수 있다.

<pre>fmap f ma = ma >>= \a -> return (f a)</pre>

완전성을 위해 `Writer` monad의 `join`은 다음과 같다.

<pre>join :: Monoid w => Writer w (Writer w a) -> Writer w a
join (Writer ((Writer (a, w')), w)) = Writer (a, w `mappend` w')</pre>

## `do` 표기법

monad를 사용해 코드를 쓰는 한 방법은 Kleisli 화살표를 물고기 연산자로 합성하는 것이다. point-free 스타일의 일반화다. point-free 코드는 간결하고 흔히 우아하지만 일반적으로 이해하기 어려워 난해함에 가까울 수 있다. 그래서 대부분의 프로그래머는 함수 인자와 중간 값에 이름 붙이는 것을 선호한다.

monad를 다룰 때는 물고기보다 bind 연산자를 선호한다는 뜻이다. bind는 monad 값을 받아 monad 값을 반환하며 프로그래머는 그 값에 이름을 붙일 수 있다. 하지만 별로 나아지지 않는다. 정말 원하는 것은 값을 감싼 monad 컨테이너가 아니라 일반 값을 다루는 척하는 것이다. 전역 로그 갱신 같은 부수 효과를 대부분 시야에서 숨기는 명령형 코드가 그렇게 작동한다. 하스켈의 `do` 표기법이 이를 흉내 낸다.

그렇다면 왜 monad를 쓰는지 궁금할 수 있다. 부수 효과를 보이지 않게 만들고 싶다면 명령형 언어를 쓰면 되지 않을까? monad는 부수 효과를 훨씬 잘 통제하게 해 준다. 예를 들어 `Writer`의 로그는 함수에서 함수로 전달되며 전역으로 노출되지 않는다. 로그를 망가뜨리거나 데이터 경쟁을 만들 가능성이 없다. monad 코드도 프로그램의 나머지 부분과 명확히 구분되어 격리된다.

`do` 표기법은 monad 합성을 위한 문법 설탕일 뿐이다. 겉으로는 명령형 코드와 매우 비슷하지만 bind와 람다 식의 연속으로 직접 변환된다.

앞서 `Writer` monad의 Kleisli 화살표 합성을 설명한 예를 보자. 현재 정의로는 다음처럼 쓸 수 있다.

<pre>process :: String -> Writer String [String]
process = upCase >=> toWords</pre>

입력 문자열의 모든 문자를 대문자로 바꾸고 단어로 나누면서 동작 로그를 만든다.

`do` 표기법으로는 다음과 같다.

<pre>process s = do
    upStr <- upCase s
    toWords upStr</pre>

`upCase`가 `Writer`를 만들지만 여기서 `upStr`은 단순한 `String`이다.

<pre>upCase :: String -> Writer String String
upCase s = Writer (map toUpper s, "upCase ")</pre>

컴파일러가 `do` 블록을 다음으로 문법 해제하기 때문이다.

<pre>process s =
   upCase s **>>= \** upStr **->**
       toWords upStr</pre>

`upCase`의 monad 결과는 `String`을 받는 람다에 bind된다. `do` 블록에는 이 문자열의 이름이 나타난다. 다음 줄을 읽을 때:

<pre>upStr <- upCase s</pre>

`upStr`이 `upCase s`의 결과를 *얻는다*고 말한다.

`toWords`를 인라인으로 넣으면 의사 명령형 스타일이 더 뚜렷해진다. 문자열 `"toWords "`를 기록하는 `tell` 호출 뒤에 `words`로 `upStr`을 나눈 결과를 `return`에 전달한다. `words`는 문자열에 작용하는 일반 함수다.

<pre>process s = do
    upStr <- upCase s
    tell "toWords "
    return (words upStr)</pre>

do 블록의 각 줄은 문법 해제된 코드에 중첩 bind를 하나씩 도입한다.

<pre>process s =
    upCase s >>= \upStr ->
      tell "toWords " >>= \() ->
        return (words upStr)</pre>

`tell`은 유닛 값을 만들므로 다음 람다에 전달할 필요가 없다. 효과, 여기서는 로그 기여는 무시하지 않으면서 monad 결과의 내용물을 무시하는 일은 흔하므로 그 경우 bind를 대체하는 특별한 연산자가 있다.

<pre>(>>) :: m a -> m b -> m b
m >> k = m >>= (\_ -> k)</pre>

코드의 실제 문법 해제 결과는 다음과 같다.

<pre>process s =
    upCase s >>= \upStr ->
      tell "toWords " >>
        return (words upStr)</pre>

일반적으로 `do` 블록은 왼쪽 화살표로 이후 코드에서 사용할 새 이름을 도입하거나 순전히 부수 효과를 위해 실행하는 줄 또는 하위 블록으로 이루어진다. 코드 줄 사이에는 bind 연산자가 암시되어 있다. 하스켈에서는 `do` 블록의 서식을 중괄호와 세미콜론으로 바꿀 수도 있다. 그래서 monad를 세미콜론을 오버로드하는 방법이라고 설명할 수 있다.

`do` 표기법을 문법 해제할 때 람다와 bind가 중첩되므로 각 줄의 결과가 나머지 `do` 블록 실행에 영향을 준다는 점에 주목하자. 이 속성으로 예외를 흉내 내는 등 복잡한 제어 구조를 도입할 수 있다.

흥미롭게도 `do` 표기법에 해당하는 것이 명령형 언어, 특히 C++에도 응용되었다. 재개 가능한 함수 또는 coroutine을 말한다. C++ [future가 monad를 이룬다](https://bartoszmilewski.com/2014/02/26/c17-i-see-a-monad-in-your-future/)는 사실은 비밀이 아니다. 곧 논의할 continuation monad의 예다. continuation은 합성하기 매우 어렵다. 하스켈에서는 `do` 표기법으로 "내 핸들러가 네 핸들러를 호출하는" 스파게티를 순차 코드처럼 바꾼다. 재개 가능한 함수는 C++에서 같은 변환을 가능하게 한다. 같은 메커니즘으로 [중첩 루프의 스파게티](https://bartoszmilewski.com/2014/04/21/getting-lazy-with-c/)를 리스트 내포나 generator로 바꿀 수 있다. 본질적으로 리스트 monad의 `do` 표기법이다. monad라는 통합 추상화가 없으면 이런 문제마다 보통 언어에 맞춤 확장을 제공한다. 하스켈에서는 모두 라이브러리로 처리한다.
