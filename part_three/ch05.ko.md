# Monad와 효과 {#monads-and-effects}

monad가 장식된 함수를 합성하게 해 준다는 목적을 알았으니, 정말 흥미로운 질문은 장식된 함수가 함수형 프로그래밍에서 왜 그토록 중요한가 하는 것이다. `Writer` monad에서 장식 덕분에 여러 함수 호출에 걸쳐 로그를 만들고 축적하는 예를 보았다. 전역 상태에 접근해 수정하는 불순 함수로 풀 법한 문제를 순수 함수로 해결했다.

## 문제

다음은 [Eugenio Moggi의 기념비적인 논문](https://doi.org/10.1016/0890-5401(91)90052-4)에서 가져온 비슷한 문제의 짧은 목록이다. 전통적으로 모두 함수의 순수성을 포기해 해결한다.

* 부분성: 끝나지 않을 수 있는 계산
* 비결정성: 결과를 여러 개 반환할 수 있는 계산
* 부수 효과: 상태에 접근하거나 수정하는 계산
    * 읽기 전용 상태 또는 환경
    * 쓰기 전용 상태 또는 로그
    * 읽기/쓰기 상태
* 예외: 실패할 수 있는 부분 함수
* continuation: 프로그램 상태를 저장했다가 필요할 때 복원하는 능력
* 대화형 입력
* 대화형 출력

놀라운 사실은 이 모든 문제를 함수를 장식한다는 같은 영리한 기법으로 해결할 수 있다는 것이다. 물론 장식은 경우마다 완전히 다르다.

이 단계에서는 장식이 monad여야 한다는 요구가 없음을 알아야 한다. 합성, 즉 장식된 함수 하나를 더 작은 장식된 함수로 분해하는 능력을 요구할 때만 monad가 필요하다. 각 장식이 다르므로 monad 합성의 구현도 다르지만 전체 패턴은 같다. 결합법칙을 만족하고 항등을 갖춘 합성이라는 아주 단순한 패턴이다.

다음 절은 하스켈 예제가 많다. 범주론으로 빨리 돌아가고 싶거나 하스켈의 monad 구현에 이미 익숙하다면 훑어보거나 건너뛰어도 좋다.

## 해법

먼저 `Writer` monad를 사용한 방식을 분석하자. 인자를 받으면 특정 출력을 만드는 순수 함수에서 시작했다. 원래 출력을 문자열과 짝지어 장식하는 다른 함수로 바꾸었다. 로깅 문제의 해법이었다.

하지만 일반적으로 하나의 거대한 해법을 다루고 싶지 않으므로 거기서 멈출 수 없었다. 로그를 만드는 함수 하나를 더 작은 로그 생성 함수들로 분해할 수 있어야 했다. 이 작은 함수들의 합성이 monad라는 개념으로 이끌었다.

정말 놀라운 것은 함수 반환 타입을 장식한다는 같은 패턴이 보통 순수성을 포기해야 하는 다양한 문제에 작동한다는 것이다. 목록을 차례로 살펴보며 각 문제에 적용할 장식을 찾자.

### 부분성

끝나지 않을 수 있는 모든 함수의 반환 타입을 원래 타입의 모든 값에 특별한 "bottom" 값 `⊥`을 더한 "끌어올린" 타입으로 바꾼다. 예를 들어 집합으로서 `Bool`에는 `True`, `False` 두 원소가 있다. 끌어올린 `Bool`에는 원소가 셋이다. 이를 반환하는 함수는 `True`, `False`를 만들거나 영원히 실행될 수 있다.

재미있게도 하스켈 같은 지연 언어에서는 끝나지 않는 함수가 실제로 값을 반환할 수 있고, 이 값을 다음 함수에 전달할 수 있다. 이 특별한 값을 bottom이라고 한다. 명시적으로 필요하지 않은 한, 이를테면 패턴 매칭하거나 출력하지 않는 한 프로그램 실행을 멈추지 않고 전달할 수 있다. 모든 하스켈 함수는 잠재적으로 끝나지 않을 수 있으므로 하스켈의 모든 타입은 끌어올려진 것으로 가정한다. 그래서 더 단순한 **Set** 대신 하스켈의 끌어올린 타입과 함수의 범주 **Hask**를 흔히 이야기한다. 다만 **Hask**가 진짜 범주인지는 분명하지 않다. [Andrej Bauer의 글](http://math.andrej.com/2016/08/06/hask-is-not-a-category/)을 보라.

### 비결정성

함수가 여러 결과를 반환할 수 있다면 한꺼번에 모두 반환해도 된다. 의미론적으로 비결정 함수는 결과 리스트를 반환하는 함수와 동등하다. 지연 평가하고 쓰레기 수집을 하는 언어에서는 매우 타당하다. 값 하나만 필요하면 리스트의 머리를 취하면 되고 꼬리는 평가되지 않는다. 임의의 값이 필요하면 난수 생성기로 리스트의 n번째 원소를 고른다. 지연성 덕분에 무한한 결과 리스트도 반환할 수 있다.

하스켈의 비결정 계산 구현인 리스트 monad에서 `join`은 `concat`으로 구현한다. `join`은 컨테이너의 컨테이너를 평평하게 해야 하며 `concat`은 리스트의 리스트를 한 리스트로 이어 붙인다. `return`은 한 원소 리스트를 만든다.

<pre>instance Monad [] where
    join = concat
    return x = [x]</pre>

리스트 monad의 bind는 일반 공식인 `fmap` 뒤에 `join`을 적용해 얻는다.

<pre>as >>= k = concat (fmap k as)</pre>

자체적으로 리스트를 만드는 함수 `k`를 리스트 `as`의 모든 원소에 적용한다. 결과인 리스트의 리스트를 `concat`으로 평평하게 만든다.

프로그래머의 관점에서 리스트를 다루는 것은 비결정 함수를 루프에서 호출하거나 iterator를 반환하는 함수를 구현하는 것보다 쉽다. 다만 [현대 C++](http://ericniebler.com/2014/04/27/range-comprehensions/)에서 지연 range를 반환하는 것은 하스켈 리스트 반환과 거의 동등하다.

비결정성을 창의적으로 사용하는 좋은 예가 게임 프로그래밍이다. 컴퓨터가 사람과 체스를 둘 때 상대의 다음 수를 예측할 수는 없지만 가능한 모든 수의 리스트를 만들고 하나씩 분석할 수 있다. 비결정 parser도 주어진 식의 가능한 모든 parse 결과 리스트를 만들 수 있다.

리스트를 반환하는 함수를 비결정 함수로 해석할 수 있지만 리스트 monad의 응용은 훨씬 넓다. 리스트를 만드는 계산을 이어 붙이면 명령형 프로그래밍의 반복 구성인 루프를 완벽하게 함수형으로 대체할 수 있기 때문이다. 루프 하나는 흔히 리스트의 각 원소에 루프 본문을 적용하는 `fmap`으로 다시 쓸 수 있다. 리스트 monad의 `do` 표기법은 복잡한 중첩 루프를 대체할 수 있다.

내가 좋아하는 예는 직각삼각형의 변을 이룰 수 있는 양의 정수 세 쌍인 피타고라스 세쌍을 만드는 프로그램이다.

<pre>triples = do
    z <- [1..]
    x <- [1..z]
    y <- [x..z]
    guard (x^2 + y^2 == z^2)
    return (x, y, z)</pre>

첫 줄에서 `z`는 양의 정수 무한 리스트 `[1..]`의 원소를 얻는다. 다음으로 `x`는 1부터 `z`까지의 유한 리스트 `[1..z]`에서 원소를 얻고, `y`는 `x`부터 `z`까지의 리스트에서 얻는다. 이제 `1 <= x <= y <= z`인 세 수가 있다. 함수 `guard`는 `Bool` 식을 받아 유닛 리스트를 반환한다.

<pre>guard :: Bool -> [()]
guard True  = [()]
guard False = []</pre>

더 큰 클래스 `MonadPlus`의 원소인 이 함수는 피타고라스 세쌍이 아닌 것을 걸러 낸다. bind 또는 관련 연산자 `>>`의 구현을 보면 빈 리스트가 주어질 때 빈 리스트를 만든다. 반대로 유닛을 담은 한 원소 리스트 `[()]`가 주어지면 bind는 continuation인 `return (x, y, z)`를 호출해 검증된 피타고라스 세쌍의 한 원소 리스트를 만든다. 바깥 bind들이 이 한 원소 리스트를 모두 이어 붙여 최종 무한 결과를 만든다. `triples`의 호출자는 전체 리스트를 소비할 수 없지만 하스켈은 지연 언어이므로 상관없다.

보통 세 겹 중첩 루프가 필요한 문제가 리스트 monad와 `do` 표기법으로 크게 단순해졌다. 하스켈의 리스트 내포를 사용하면 더 단순하게 만들 수도 있다.

<pre>triples = [(x, y, z) | z <- [1..]
                     , x <- [1..z]
                     , y <- [x..z]
                     , x^2 + y^2 == z^2]</pre>

리스트 monad, 엄밀히는 `MonadPlus`를 위한 문법 설탕이 더해진 것일 뿐이다. 다른 함수형 또는 명령형 언어에서도 generator와 coroutine이라는 모습으로 비슷한 구성을 볼 수 있다.

### 읽기 전용 상태

외부 상태 또는 환경에 읽기 전용으로 접근하는 함수는 언제나 그 환경을 추가 인자로 받는 함수로 바꿀 수 있다. `e`가 환경 타입일 때 순수 함수 `(a, e) -> b`는 처음에는 Kleisli 화살표처럼 보이지 않는다. 하지만 `a -> (e -> b)`로 커링하면 장식이 오랜 친구 reader functor임을 알아볼 수 있다.

<pre>newtype Reader e a = Reader (e -> a)</pre>

`Reader`를 반환하는 함수는 환경이 주어지면 원하는 결과를 만드는 작은 실행 파일, 즉 동작을 만든다고 해석할 수 있다. 그런 동작을 실행하는 도우미 함수 `runReader`가 있다.

<pre>runReader :: Reader e a -> e -> a
runReader (Reader f) e = f e</pre>

환경 값이 다르면 다른 결과를 만들 수 있다. `Reader`를 반환하는 함수와 `Reader` 동작 자체가 모두 순수하다는 점에 주목하자.

`Reader` monad의 bind를 구현하려면 먼저 환경 `e`를 받아 `b`를 만드는 함수를 만들어야 한다.

<pre>ra >>= k = Reader (\e -> ...)</pre>

람다 안에서 동작 `ra`를 실행해 `a`를 만든다.

<pre>ra >>= k = Reader (\e -> let a = runReader ra e
                         in ...)</pre>

`a`를 continuation `k`에 전달해 새 동작 `rb`를 얻는다.

<pre>ra >>= k = Reader (\e -> let a  = runReader ra e
                             rb = k a
                         in ...)</pre>

마지막으로 환경 `e`로 동작 `rb`를 실행한다.

<pre>ra >>= k = Reader (\e -> let a  = runReader ra e
                             rb = k a
                         in runReader rb e)</pre>

`return`은 환경을 무시하고 바뀌지 않은 값을 반환하는 동작으로 구현한다. 약간 단순화해 모두 합치면 다음과 같다.

<pre>instance Monad (Reader e) where
    ra >>= k = Reader (\e -> runReader (k (runReader ra e)) e)
    return x = Reader (\e -> x)</pre>

### 쓰기 전용 상태

처음의 로깅 예일 뿐이다. `Writer` functor가 장식을 제공한다.

<pre>newtype Writer w a = Writer (a, w)</pre>

완전성을 위해 데이터 생성자를 풀어내는 단순한 도우미 `runWriter`도 있다.

<pre>runWriter :: Writer w a -> (a, w)
runWriter (Writer (a, w)) = (a, w)</pre>

앞에서 보았듯 `Writer`를 합성 가능하게 하려면 `w`가 모노이드여야 한다. bind로 쓴 `Writer`의 monad 인스턴스는 다음과 같다.

<pre>instance (Monoid w) => Monad (Writer w) where
    (Writer (a, w)) >>= k = let (a', w') = runWriter (k a)
                            in Writer (a', w `mappend` w')
    return a = Writer (a, mempty)</pre>

### 상태

상태에 읽기/쓰기 접근을 하는 함수는 `Reader`와 `Writer`의 장식을 결합한다. 상태를 추가 인자로 받고 값/상태 쌍을 결과로 만드는 순수 함수 `(a, s) -> (b, s)`로 생각할 수 있다. 커링하면 `a -> (s -> (b, s))` 형태의 Kleisli 화살표가 되고 장식은 `State` functor로 추상화된다.

<pre>newtype State s a = State (s -> (a, s))</pre>

Kleisli 화살표가 도우미 함수로 실행할 수 있는 동작을 반환한다고 볼 수 있다.

<pre>runState :: State s a -> s -> (a, s)
runState (State f) s = f s</pre>

처음 상태가 다르면 결과뿐 아니라 마지막 상태도 다를 수 있다.

`State` monad의 bind 구현은 `Reader`와 매우 비슷하지만 각 단계에서 올바른 상태를 전달하도록 조심해야 한다.

<pre>sa >>= k = State (\s -> let (a, s') = runState sa s
                            sb = k a
                        in runState sb s')</pre>

전체 인스턴스는 다음과 같다.

<pre>instance Monad (State s) where
    sa >>= k = State (\s -> let (a, s') = runState sa s
                            in runState (k a) s')
    return a = State (\s -> (a, s))</pre>

상태 조작에 사용할 수 있는 도우미 Kleisli 화살표도 둘 있다. 하나는 상태를 검사하도록 가져온다.

<pre>get :: State s s
get = State (\s -> (s, s))</pre>

다른 하나는 완전히 새로운 상태로 바꾼다.

<pre>put :: s -> State s ()
put s' = State (\s -> ((), s'))</pre>

### 예외

예외를 던지는 명령형 함수는 실제로 일부 인자 값에 정의되지 않은 부분 함수다. 순수한 전함수로 예외를 가장 단순하게 구현하려면 `Maybe` functor를 사용한다. 부분 함수를, 의미가 있을 때 `Just a`를 반환하고 그렇지 않을 때 `Nothing`을 반환하는 전함수로 확장한다. 실패 원인에 관한 정보도 반환하려면 첫 타입을 이를테면 `String`으로 고정한 `Either` functor를 사용할 수 있다.

`Maybe`의 `Monad` 인스턴스는 다음과 같다.

<pre>instance Monad Maybe where
    Nothing >>= k = Nothing
    Just a  >>= k = k a
    return a = Just a</pre>

`Maybe`의 monad 합성은 오류가 발견되면 계산을 올바르게 단축한다. continuation `k`는 호출되지 않는다. 예외에서 기대하는 동작이다.

### Continuation

취업 면접 뒤에 겪을 수 있는 "전화하지 마세요, 저희가 연락드리겠습니다!" 상황이다. 직접 답을 받는 대신 결과와 함께 호출될 함수인 핸들러를 제공해야 한다. 호출 시점에 결과를 알 수 없을 때 특히 유용하다. 다른 스레드가 계산하거나 원격 웹사이트에서 전달하는 경우가 그렇다. 이 경우 Kleisli 화살표는 "계산의 나머지"를 나타내는 핸들러를 받는 함수를 반환한다.

<pre>data Cont r a = Cont ((a -> r) -> r)</pre>

핸들러 `a -> r`은 마침내 호출되면 타입 `r`의 결과를 만들고 이 결과가 끝에서 반환된다. continuation은 결과 타입으로 매개변수화된다. 실제로는 흔히 어떤 상태 표시자다.

Kleisli 화살표가 반환한 동작을 실행하는 도우미 함수도 있다. 핸들러를 받아 continuation에 전달한다.

<pre>runCont :: Cont r a -> (a -> r) -> r
runCont (Cont k) h = k h</pre>

continuation은 합성이 악명 높게 어려우므로 monad, 특히 `do` 표기법으로 다루면 큰 이점이 있다.

bind 구현을 알아내자. 먼저 장식을 벗긴 시그니처를 보자.

<pre>(>>=) :: ((a -> r) -> r) ->
         (a -> (b -> r) -> r) ->
         ((b -> r) -> r)</pre>

목표는 핸들러 `(b -> r)`을 받아 결과 `r`을 만드는 함수이므로 다음에서 시작한다.

<pre>ka >>= kab = Cont (\hb -> ...)</pre>

람다 안에서 계산의 나머지를 나타내는 적절한 핸들러로 함수 `ka`를 호출하고 싶다. 이 핸들러를 람다로 구현한다.

<pre>runCont ka (\a -> ...)</pre>

계산의 나머지는 먼저 `a`로 `kab`를 호출한 다음 결과 동작 `kb`에 `hb`를 전달하는 것이다.

<pre>runCont ka (\a -> let kb = kab a
                  in runCont kb hb)</pre>

continuation은 안에서 밖으로 합성된다. 최종 핸들러 `hb`는 계산의 가장 안쪽 층에서 호출된다. 전체 인스턴스는 다음과 같다.

<pre>instance Monad (Cont r) where
    ka >>= kab = Cont (\hb -> runCont ka (\a -> runCont (kab a) hb))
    return a = Cont (\ha -> ha a)</pre>

### 대화형 입력

가장 까다롭고 혼란을 많이 일으키는 문제다. `getChar` 같은 함수가 키보드로 입력한 문자를 반환한다면 순수할 수 없다. 하지만 컨테이너 안에 문자를 넣어 반환한다면 어떨까? 컨테이너에서 문자를 꺼낼 방법이 없다면 함수가 순수하다고 주장할 수 있다. `getChar`를 호출할 때마다 정확히 같은 컨테이너를 반환한다. 개념적으로는 가능한 모든 문자의 중첩을 담는다.

양자역학에 익숙하다면 이 비유를 이해하기 어렵지 않다. Schrödinger의 고양이가 든 상자와 같지만 상자를 열거나 들여다볼 방법이 없다. 상자는 특별한 내장 `IO` functor로 정의한다. `getChar`는 Kleisli 화살표로 선언할 수 있다.

<pre>getChar :: () -> IO Char</pre>

유닛 타입에서 출발하는 함수는 반환 타입의 값을 고르는 것과 동등하므로 실제 선언은 `getChar :: IO Char`로 단순화한다.

functor인 `IO`는 `fmap`으로 내용물을 조작하게 해 준다. 문자뿐 아니라 모든 타입의 내용물을 저장할 수 있다. 하스켈에서 `IO`가 monad라는 사실을 생각하면 이 접근의 진짜 쓸모가 드러난다. `IO` 객체를 만드는 Kleisli 화살표를 합성할 수 있다.

Kleisli 합성으로 `IO` 객체의 내용물을 들여다볼 수 있다고 생각할 수 있다. 양자 비유를 계속하면 "파동 함수를 붕괴"시키는 셈이다. 실제로 `getChar`를 문자를 받아 정수로 바꾸는 다른 Kleisli 화살표와 합성할 수 있다. 하지만 두 번째 화살표도 정수를 `(IO Int)`로만 반환할 수 있다. 다시 가능한 모든 정수의 중첩을 얻는다. 계속 마찬가지다. Schrödinger의 고양이는 절대 자루 밖으로 나오지 않는다. `IO` monad 안에 들어가면 빠져나갈 방법이 없다. `IO`에는 `runState`나 `runReader`에 해당하는 것이 없다. `runIO`는 없다!

Kleisli 화살표의 결과인 `IO` 객체를 다른 화살표와 합성하는 것 외에 무엇을 할 수 있을까? `main`에서 반환할 수 있다. 하스켈에서 `main`의 시그니처는 다음과 같다.

<pre>main :: IO ()</pre>

Kleisli 화살표로 생각해도 된다.

<pre>main :: () -> IO ()</pre>

이 관점에서 하스켈 프로그램은 `IO` monad의 거대한 Kleisli 화살표 하나다. monad 합성으로 더 작은 화살표들을 합성해 만들 수 있다. 결과 `IO` 객체, 즉 `IO` 동작으로 무언가 하는 것은 런타임 시스템의 몫이다.

화살표 자체는 순수 함수이며 끝까지 순수 함수뿐이라는 점에 주목하자. 더러운 일은 시스템에 맡긴다. `main`이 반환한 `IO` 동작을 마침내 실행할 때 사용자 입력 읽기, 파일 수정, 불쾌한 메시지 출력, 디스크 포맷 같은 온갖 지저분한 일을 한다. 하스켈 프로그램은 손을 더럽히지 않는다. `unsafePerformIO`를 호출할 때는 예외지만 다른 이야기다.

하스켈은 지연 언어이므로 `main`은 거의 즉시 반환하고 더러운 일이 바로 시작된다. `IO` 동작을 실행하는 동안 순수 계산의 결과를 요청해 필요할 때 평가한다. 실제 프로그램 실행은 순수한 하스켈 코드와 더러운 시스템 코드가 교차하는 과정이다.

더 기괴하지만 수학 모형으로 완벽히 말이 되는 `IO` monad의 대안 해석도 있다. 우주 전체를 프로그램의 객체로 취급한다. 개념적으로 명령형 모형은 우주를 외부 전역 객체로 취급하므로 I/O 절차는 그 객체와 상호작용해 부수 효과를 일으킨다. 우주의 상태를 읽고 수정할 수 있다.

함수형 프로그래밍에서 상태를 다루는 법은 이미 안다. state monad를 사용한다. 하지만 단순한 상태와 달리 우주의 상태는 표준 데이터 구조로 쉽게 설명할 수 없다. 직접 상호작용하지 않는 한 설명할 필요도 없다. 타입 `RealWorld`가 존재하고 우주 공학의 기적으로 런타임이 이 타입의 객체를 제공한다고 가정하면 충분하다. `IO` 동작은 함수일 뿐이다.

<pre>type IO a  =  RealWorld -> (a, RealWorld)</pre>

`State` monad로 쓰면:

<pre>type IO = State RealWorld</pre>

다만 `IO` monad의 `>=>`와 `return`은 언어에 내장되어야 한다.

### 대화형 출력

같은 `IO` monad로 대화형 출력을 캡슐화한다. `RealWorld`는 모든 출력 장치를 포함한다고 가정한다. 하스켈에서 출력 함수를 호출하고 아무 일도 하지 않는 척하면 왜 안 되는지 궁금할 수 있다. 예를 들어 왜 다음이 아니라:

<pre>putStr :: String -> IO ()</pre>

더 단순한 다음 시그니처를 쓰지 않을까?

<pre>putStr :: String -> ()</pre>

이유는 둘이다. 하스켈은 지연 언어라서 결과인 유닛 객체가 어디에도 사용되지 않는 함수는 절대 호출하지 않는다. 지연 언어가 아니더라도 그런 호출의 순서를 자유롭게 바꿔 출력을 망칠 수 있다. 하스켈에서 두 함수의 순차 실행을 강제하는 유일한 방법은 데이터 의존성이다. 한 함수의 입력이 다른 함수의 출력에 의존해야 한다. `IO` 동작 사이에 `RealWorld`를 전달하면 순서가 강제된다.

개념적으로 다음 프로그램에서:

<pre>main :: IO ()
main = do
    putStr "Hello "
    putStr "World!"</pre>

"World!"를 출력하는 동작은 화면에 이미 "Hello "가 있는 우주를 입력으로 받는다. 화면에 "Hello World!"가 있는 새 우주를 출력한다.

## 결론

물론 monad 프로그래밍의 표면만 살짝 긁었다. monad는 명령형 프로그래밍에서 보통 부수 효과로 하는 일을 순수 함수로 수행할 뿐 아니라 높은 수준의 제어와 타입 안전성을 갖추고 수행한다. 단점이 없는 것은 아니다. 가장 큰 불만은 monad끼리 쉽게 합성되지 않는다는 것이다. 기본 monad 대부분은 monad transformer 라이브러리로 결합할 수 있다. 이를테면 상태와 예외를 결합한 monad 스택은 비교적 쉽게 만들 수 있지만 임의의 monad를 함께 쌓는 공식은 없다.
