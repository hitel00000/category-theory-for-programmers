# Functoriality

이제 functor가 무엇인지 알고 몇 가지 예도 보았으니, 작은 functor로 더 큰 functor를 만드는 방법을 살펴보자. 특히 어떤 타입 생성자, 즉 범주의 객체 사이 사상에 해당하는 것이 사상 사이 사상까지 포함하는 functor로 확장될 수 있는지 알아보는 것은 흥미롭다.

## Bifunctor

functor는 *Cat*, 즉 범주들의 범주에서 사상이므로 사상, 특히 함수에 관한 직관의 상당 부분을 functor에도 적용할 수 있다. 예를 들어 인자를 두 개 받는 함수가 있을 수 있듯이 인자를 두 개 받는 functor, 즉 *bifunctor*도 있을 수 있다. 객체에 대해 bifunctor는 범주 C에서 하나, 범주 D에서 하나씩 가져온 모든 객체 쌍을 범주 E의 객체로 보낸다. 이는 범주들의 *데카르트 곱* C×D에서 E로 가는 사상이라는 뜻일 뿐이다.

![](images/bifunctor.jpg)

여기까지는 아주 간단하다. 하지만 functoriality에 따르면 bifunctor는 사상도 보내야 한다. 이번에는 C에서 하나, D에서 하나씩 가져온 사상 쌍을 E의 사상 하나로 보내야 한다.

다시 말해 사상 쌍은 곱 범주 C×D의 사상 하나일 뿐이다. 범주의 데카르트 곱에서 사상은 한 객체 쌍에서 다른 객체 쌍으로 가는 사상 쌍으로 정의한다. 이 사상 쌍들은 당연한 방식으로 합성할 수 있다.

```haskell
(f, g) ∘ (f', g') = (f ∘ f', g ∘ g')
```

이 합성은 결합법칙을 만족하며 항등, 즉 항등 사상 쌍 *(id, id)*을 가진다. 따라서 범주의 데카르트 곱은 실제로 범주다.

하지만 bifunctor를 더 쉽게 생각하는 방법은 두 인자 각각에 대해 functor라고 보는 것이다. 그러므로 결합법칙과 항등 보존이라는 functor 법칙을 bifunctor에 맞게 옮기는 대신, 각 인자에 대해 따로 확인하는 것으로 충분하다. 범주 쌍에서 세 번째 범주로 가는 사상이 있고, 다른 인자를 고정한 채 각 인자에 대해 그 사상이 functorial하다는 것을 증명한다면 그 사상은 자동으로 bifunctor다. 여기서 *functorial하다*는 말은 사상에 대해 제대로 된 functor처럼 작용한다는 뜻이다.

하스켈에서 bifunctor를 정의해 보자. 이 경우 세 범주는 모두 같은 범주, 즉 하스켈 타입의 범주다. bifunctor는 타입 인자를 두 개 받는 타입 생성자다. 다음은 `Control.Bifunctor` 라이브러리에서 그대로 가져온 `Bifunctor` 타입 클래스 정의다.

```haskell
class Bifunctor f where
    bimap :: (a -> c) -> (b -> d) -> f a b -> f c d
    bimap g h = first g . second h
    first :: (a -> c) -> f a b -> f c b
    first g = bimap g id
    second :: (b -> d) -> f a b -> f a d
    second = bimap id
```

타입 변수 `f`는 bifunctor를 나타낸다. 모든 타입 시그니처에서 언제나 타입 인자 두 개에 적용되는 것을 볼 수 있다. 첫 번째 타입 시그니처는 두 함수를 한꺼번에 보내는 `bimap`을 정의한다. 결과는 끌어올려진 함수 `(f a b -> f c d)`로, bifunctor의 타입 생성자가 만든 타입에 작용한다. `first`와 `second`로 표현한 `bimap`의 기본 구현도 있다. 이는 각 인자에 대한 functoriality만 있으면 bifunctor를 정의할 수 있음을 보여 준다.

타입 클래스 정의는 둘 모두에 대해 `bimap`으로 표현한 기본 구현을 제공한다.

`Bifunctor` 인스턴스를 선언할 때는 `bimap`을 구현하고 `first`와 `second`의 기본 구현을 받아들이거나, `first`와 `second`를 모두 구현하고 `bimap`의 기본 구현을 받아들이는 방법 중에서 고를 수 있다. 물론 셋을 모두 구현할 수도 있지만, 그때는 이들이 위와 같은 관계를 만족하도록 직접 보장해야 한다.

## 곱과 쌍대곱 Bifunctor

bifunctor의 중요한 예는 [보편적 구성](#products-and-coproducts)으로 정의한 두 객체의 곱, 즉 범주론적 곱이다. 임의의 객체 쌍에 대해 곱이 존재한다면 그 객체들에서 곱으로 가는 사상은 bifunctorial하다. 이는 일반적으로도 참이고 하스켈에서도 참이다. 다음은 가장 단순한 곱 타입인 쌍 생성자의 `Bifunctor` 인스턴스다.

```haskell
instance Bifunctor (,) where
    bimap f g (x, y) = (f x, g y)
```

선택의 여지가 별로 없다. `bimap`은 첫 번째 함수를 쌍의 첫 번째 성분에 적용하고 두 번째 함수를 두 번째 성분에 적용할 뿐이다. 타입이 주어지면 코드는 사실상 저절로 작성된다.

```haskell
bimap :: (a -> c) -> (b -> d) -> (a, b) -> (c, d)
```

여기서 bifunctor는 타입들의 쌍을 만드는 방식으로 작용한다. 예를 들면 다음과 같다.

```haskell
(,) a b = (a, b)
```

쌍대성에 따라 범주의 모든 객체 쌍에 대해 쌍대곱이 정의되어 있다면 쌍대곱 역시 bifunctor다. 하스켈에서는 `Either` 타입 생성자가 `Bifunctor`의 인스턴스인 것으로 이를 확인할 수 있다.

```haskell
instance Bifunctor Either where
    bimap f _ (Left x)  = Left (f x)
    bimap _ g (Right y) = Right (g y)
```

이 코드도 저절로 작성된다.

모노이드 범주를 이야기했을 때를 기억하는가? 모노이드 범주는 객체에 작용하는 이항 연산자와 단위 객체를 정의한다. `Set`은 한 원소 집합을 단위로 하는 데카르트 곱에 관해 모노이드 범주라고 했다. 또한 공집합을 단위로 하는 분리합에 관해서도 모노이드 범주다. 그때 말하지 않은 요구 조건 중 하나는 모노이드 범주의 이항 연산자가 bifunctor여야 한다는 것이다. 이는 매우 중요한 요구 조건이다. 모노이드 곱이 사상으로 정의되는 범주의 구조와 양립하기를 원하기 때문이다. 이제 모노이드 범주의 완전한 정의에 한 걸음 더 가까워졌다. 거기에 이르려면 아직 자연성에 대해 배워야 한다.

## Functorial 대수적 데이터 타입

지금까지 매개변수화된 데이터 타입 중 `fmap`을 정의할 수 있어 functor가 되는 예를 여럿 보았다. 복잡한 데이터 타입은 더 단순한 데이터 타입으로 구성한다. 특히 대수적 데이터 타입(ADT)은 합과 곱을 사용해 만든다. 방금 합과 곱이 functorial하다는 것을 보았다. 또한 functor가 합성된다는 사실도 안다. 그러므로 ADT의 기본 구성 요소가 functorial함을 보일 수 있다면 매개변수화된 ADT 역시 functorial하다는 것을 알 수 있다.

그렇다면 매개변수화된 대수적 데이터 타입의 구성 요소는 무엇일까? 먼저 `Maybe`의 `Nothing`이나 `List`의 `Nil`처럼 functor의 타입 매개변수에 의존하지 않는 항목이 있다. 이것들은 `Const` functor와 동등하다. `Const` functor는 자신의 타입 매개변수를 무시한다는 것을 기억하자. 정확히는 우리가 관심을 두는 *두 번째* 타입 매개변수를 무시하고 첫 번째 매개변수는 상수로 유지한다.

다음으로 `Maybe`의 `Just`처럼 타입 매개변수 자체를 감쌀 뿐인 원소가 있다. 이것들은 항등 functor와 동등하다. 앞서 항등 functor를 *Cat*의 항등 사상으로 언급했지만 하스켈 정의는 제시하지 않았다. 정의는 다음과 같다.

```haskell
data Identity a = Identity a
```

```haskell
instance Functor Identity where
    fmap f (Identity x) = Identity (f x)
```

`Identity`는 `a` 타입의 불변 값 하나를 언제나 저장하는, 가능한 가장 단순한 컨테이너라고 생각할 수 있다.

대수적 데이터 구조의 나머지 모든 것은 이 두 원시 요소에 곱과 합을 사용해 만든다.

이 새로운 지식을 바탕으로 `Maybe` 타입 생성자를 다시 살펴보자.

```haskell
data Maybe a = Nothing | Just a
```

두 타입의 합이고, 합이 functorial하다는 것을 이제 안다. 첫 번째 부분인 `Nothing`은 `a`에 작용하는 `Const ()`로 나타낼 수 있다. `Const`의 첫 번째 타입 매개변수는 유닛으로 설정한다. 나중에는 `Const`의 더 흥미로운 용도를 보게 될 것이다. 두 번째 부분은 항등 functor에 다른 이름을 붙인 것일 뿐이다. 동형을 무시하면 `Maybe`를 다음처럼 정의할 수도 있었다.

```haskell
type Maybe a = Either (Const () a) (Identity a)
```

따라서 `Maybe`는 bifunctor `Either`와 두 functor `Const ()`, `Identity`의 합성이다. `Const`는 사실 bifunctor지만 여기서는 언제나 부분 적용해서 사용한다.

functor의 합성이 functor라는 것은 이미 보았다. bifunctor에도 같은 사실이 성립한다는 것을 쉽게 확인할 수 있다. bifunctor와 두 functor의 합성이 사상에 어떻게 작용하는지만 알아내면 된다. 두 사상이 주어지면 하나는 한 functor로, 다른 하나는 다른 functor로 끌어올린다. 그런 다음 끌어올린 사상 쌍을 bifunctor로 끌어올린다.

이 합성을 하스켈로 표현할 수 있다. bifunctor `bf`, 두 functor `fu`와 `gu`, 일반 타입 `a`와 `b`로 매개변수화된 데이터 타입을 정의해 보자. `bf`는 타입 두 개를 인자로 받는 타입 생성자인 타입 변수이고, `fu`와 `gu`는 각각 타입 변수 하나를 받는 타입 생성자다. `fu`를 `a`에, `gu`를 `b`에 적용한 다음 그 결과 타입 두 개에 `bf`를 적용한다.

```haskell
newtype BiComp bf fu gu a b = BiComp (bf (fu a) (gu b))
```

이는 객체, 즉 타입에 대한 합성이다. 하스켈에서는 함수를 인자에 적용하듯 타입 생성자를 타입에 적용한다는 점에 주목하자. 문법도 같다.

조금 길을 잃은 것 같다면 `BiComp`에 `Either`, `Const ()`, `Identity`, `a`, `b`를 이 순서대로 적용해 보라. 그러면 앞에서 본 간소한 `Maybe b`를 되찾을 것이다. `a`는 무시된다.

새 데이터 타입 `BiComp`는 `a`와 `b`에 대해 bifunctor지만, `bf` 자체가 `Bifunctor`이고 `fu`와 `gu`가 `Functor`일 때만 그렇다. 컴파일러는 `bf`에 사용할 수 있는 `bimap` 정의와 `fu`, `gu`에 사용할 수 있는 `fmap` 정의가 있음을 알아야 한다. 하스켈에서는 이를 인스턴스 선언의 전제 조건, 즉 클래스 제약의 집합 뒤에 이중 화살표를 붙여 표현한다.

```haskell
instance (Bifunctor bf, Functor fu, Functor gu) =>
  Bifunctor (BiComp bf fu gu) where
    bimap f1 f2 (BiComp x) = BiComp ((bimap (fmap f1) (fmap f2)) x)

```

`BiComp`의 `bimap` 구현은 `bf`의 `bimap`과 `fu`, `gu`의 두 `fmap`으로 주어진다. `BiComp`를 사용할 때마다 컴파일러가 모든 타입을 자동으로 추론하고 올바른 오버로드 함수를 고른다.

`bimap` 정의 안의 `x`는 다음 타입이다.

```haskell
bf (fu a) (gu b)
```

상당히 복잡해 보인다. 바깥쪽 `bimap`은 바깥 `bf` 층을 뚫고 들어가며, 두 `fmap`은 각각 `fu`와 `gu` 아래로 파고든다. `f1`과 `f2`의 타입이 다음과 같다면:

```haskell
f1 :: a -> a'
f2 :: b -> b'
```

최종 결과의 타입은 `bf (fu a') (gu b')`이다.

```haskell
bimap (fu a -> fu a') -> (gu b -> gu b')
  -> bf (fu a) (gu b) -> bf (fu a') (gu b')
```

직소 퍼즐을 좋아한다면 이런 타입 조작으로 몇 시간이고 즐길 수 있다.

결국 `Maybe`가 functor임을 따로 증명할 필요가 없었다. 두 functorial 원시 요소의 합으로 구성한 방식에서 그 사실이 따라 나왔다.

눈치 빠른 독자라면 이런 질문을 할지도 모른다. 대수적 데이터 타입의 `Functor` 인스턴스를 이끌어 내는 과정이 이토록 기계적이라면 자동화해서 컴파일러가 수행할 수 있지 않을까? 실제로 가능하며, 그렇게 동작한다. 소스 파일 맨 위에 다음 줄을 넣어 특정 하스켈 확장을 활성화해야 한다.

```haskell
{-# LANGUAGE DeriveFunctor #-}
```

그런 다음 데이터 구조에 `deriving Functor`를 추가한다.

```haskell
data Maybe a = Nothing | Just a
  deriving Functor
```

그러면 이에 해당하는 `fmap`이 자동으로 구현된다.

대수적 데이터 구조의 규칙성 덕분에 `Functor`뿐 아니라 앞에서 언급한 `Eq`를 비롯한 여러 타입 클래스의 인스턴스를 유도할 수 있다. 컴파일러가 직접 만든 타입 클래스의 인스턴스를 유도하도록 가르칠 수도 있지만 이는 조금 더 고급 주제다. 그래도 발상은 같다. 기본 구성 요소와 합, 곱에 대한 동작을 제공하고 나머지는 컴파일러가 알아내게 한다.

## C++의 Functor

C++ 프로그래머라면 functor 구현에 관한 한 당연히 모든 것을 직접 해야 한다. 그래도 C++에서 몇몇 대수적 데이터 구조를 알아볼 수는 있을 것이다. 그런 데이터 구조를 제네릭 템플릿으로 만들었다면 `fmap`도 빠르게 구현할 수 있을 것이다.

트리 데이터 구조를 살펴보자. 하스켈에서는 재귀적인 합 타입으로 다음처럼 정의할 수 있다.

```haskell
data Tree a = Leaf a | Node (Tree a) (Tree a)
    deriving Functor
```

앞서 말했듯 C++에서 합 타입을 구현하는 한 가지 방법은 클래스 계층을 사용하는 것이다. 객체 지향 언어라면 `fmap`을 기반 클래스 `Functor`의 가상 함수로 구현하고 모든 하위 클래스에서 재정의하는 것이 자연스러워 보일 것이다. 안타깝게도 `fmap`은 자신이 작용하는 객체의 타입, 즉 `this` 포인터뿐 아니라 적용할 함수의 반환 타입으로도 매개변수화된 템플릿이므로 불가능하다. C++에서는 가상 함수를 템플릿으로 만들 수 없다. 여기서는 `fmap`을 제네릭 자유 함수로 구현하고 패턴 매칭은 `dynamic_cast`로 대체하겠다.

동적 캐스팅을 지원하려면 기반 클래스가 가상 함수를 적어도 하나 정의해야 한다. 따라서 소멸자를 가상으로 만들겠다. 어느 경우든 좋은 선택이다.

```cpp
template<class T>
struct Tree {
    virtual ~Tree() {};
};
```

`Leaf`는 사실 모습만 바꾼 `Identity` functor다.

```cpp
template<class T>
struct Leaf : public Tree<T> {
    T _label;
    Leaf(T l) : _label(l) {}
};
```

`Node`는 곱 타입이다.

```cpp
template<class T>
struct Node : public Tree<T> {
    Tree<T> * _left;
    Tree<T> * _right;
    Node(Tree<T> * l, Tree<T> * r) : _left(l), _right(r) {}
};
```

`fmap`을 구현할 때는 `Tree`의 타입에 대한 동적 디스패치를 이용한다. `Leaf` 경우에는 `Identity` 버전의 `fmap`을 적용하고, `Node` 경우에는 `Tree` functor 두 개와 합성된 bifunctor처럼 다룬다. C++ 프로그래머에게는 이런 관점으로 코드를 분석하는 일이 익숙하지 않을 수 있지만, 범주론적으로 사고하는 좋은 연습이다.

```cpp
template<class A, class B>
Tree<B> * fmap(std::function<B(A)> f, Tree<A> * t)
{
    Leaf<A> * pl = dynamic_cast <Leaf<A>*>(t);
    if (pl)
        return new Leaf<B>(f (pl->_label));
    Node<A> * pn = dynamic_cast<Node<A>*>(t);
    if (pn)
        return new Node<B>( fmap<A>(f, pn->_left)
                          , fmap<A>(f, pn->_right));
    return nullptr;
}
```

간단하게 설명하려고 메모리와 자원 관리 문제는 무시했다. 실제 제품 코드라면 정책에 따라 고유 또는 공유 스마트 포인터를 사용하게 될 것이다.

하스켈의 `fmap` 구현과 비교해 보자.

```haskell
instance Functor Tree where
    fmap f (Leaf a) = Leaf (f a)
    fmap f (Node t t') = Node (fmap f t) (fmap f t')
```

이 구현 역시 컴파일러가 자동으로 유도할 수 있다.

## Writer Functor

앞에서 설명한 [Kleisli 범주](#kleisli-categories)로 다시 돌아오겠다고 약속했다. 그 범주의 사상은 `Writer` 데이터 구조를 반환하는 "장식된" 함수로 나타냈다.

```haskell
type Writer a = (a, String)
```

그 장식이 어떤 식으로든 endofunctor와 관련 있다고 말했다. 실제로 `Writer` 타입 생성자는 `a`에 대해 functorial하다. 단순한 곱 타입일 뿐이므로 `fmap`을 직접 구현할 필요조차 없다.

그렇다면 일반적으로 Kleisli 범주와 functor 사이에는 어떤 관계가 있을까? Kleisli 범주도 범주이므로 합성과 항등을 정의한다. 합성은 물고기 연산자로 주어진다는 것을 다시 떠올려 보자.

```haskell
(>=>) :: (a -> Writer b) -> (b -> Writer c) -> (a -> Writer c)
m1 >=> m2 = \x ->
    let (y, s1) = m1 x
        (z, s2) = m2 y
    in (z, s1 ++ s2)
```

항등 사상은 `return`이라는 함수로 정의한다.

```haskell
return :: a -> Writer a
return x = (x, "")
```

이 두 함수의 타입을 충분히 오래, 정말 *오랫동안* 들여다보면 이들을 조합해 `fmap` 역할에 맞는 타입 시그니처의 함수를 만드는 방법을 찾아낼 수 있다. 다음과 같다.

```haskell
fmap f = id >=> (\x -> return (f x))
```

여기서 물고기 연산자는 두 함수를 결합한다. 하나는 익숙한 `id`이고, 다른 하나는 람다 인자에 `f`를 적용한 결과에 `return`을 적용하는 람다다. 아마 가장 이해하기 어려운 부분은 `id`를 사용하는 이유일 것이다. 물고기 연산자의 인자는 "일반" 타입을 받아 장식된 타입을 반환하는 함수여야 하지 않는가? 꼭 그렇지는 않다. `a -> Writer b`의 `a`가 "일반" 타입이어야 한다고 말한 사람은 아무도 없다. 이는 타입 변수이므로 무엇이든 될 수 있고, 특히 `Writer b` 같은 장식된 타입도 될 수 있다.

따라서 `id`는 `Writer a`를 받아 `Writer a`로 바꾼다. 물고기 연산자는 `a` 값을 꺼내 람다의 `x`로 넘긴다. 그곳에서 `f`가 값을 `b`로 바꾸고, `return`이 이를 장식해 `Writer b`로 만든다. 모두 합치면 `Writer a`를 받아 `Writer b`를 반환하는 함수가 된다. 바로 `fmap`이 만들어야 하는 것이다.

이 논증이 매우 일반적이라는 점에 주목하자. `Writer`를 어떤 타입 생성자로든 바꿀 수 있다. 그 타입 생성자가 물고기 연산자와 `return`을 지원하기만 하면 `fmap`도 정의할 수 있다. 따라서 Kleisli 범주의 장식은 언제나 functor다. 다만 모든 functor가 Kleisli 범주를 만드는 것은 아니다.

방금 정의한 `fmap`이 컴파일러가 `deriving Functor`로 유도해 주는 `fmap`과 같은지 궁금할 수 있다. 흥미롭게도 같다. 이는 하스켈이 다형 함수를 구현하는 방식 때문이다. 이를 *매개변수 다형성*이라고 하며, 이른바 *공짜 정리*의 원천이다. 그 정리 가운데 하나에 따르면 어떤 타입 생성자에 대해 항등을 보존하는 `fmap` 구현이 존재한다면 그 구현은 유일해야 한다.

## 공변 Functor와 반변 Functor

writer functor를 다시 살펴보았으니 reader functor로 돌아가자. reader functor는 부분 적용된 함수 화살표 타입 생성자를 바탕으로 했다.

```haskell
(->) r
```

타입 동의어로 다시 쓸 수 있다.

```haskell
type Reader r a = r -> a
```

앞에서 보았듯 그 `Functor` 인스턴스는 다음과 같다.

```haskell
instance Functor (Reader r) where
    fmap f g = f . g
```

하지만 쌍 타입 생성자나 `Either` 타입 생성자와 마찬가지로 함수 타입 생성자도 타입 인자를 두 개 받는다. 쌍과 `Either`는 두 인자 모두에 대해 functorial했으므로 bifunctor였다. 함수 생성자도 bifunctor일까?

첫 번째 인자에 대해 functorial하게 만들어 보자. 먼저 `Reader`의 인자 순서만 뒤집은 타입 동의어로 시작한다.

```haskell
type Op r a = a -> r
```

이번에는 반환 타입 `r`을 고정하고 인자 타입 `a`를 바꾼다. 다음 타입 시그니처를 가지는 `fmap`을 구현하도록 타입을 어떻게든 맞출 수 있는지 살펴보자.

```haskell
fmap :: (a -> b) -> (a -> r) -> (b -> r)
```

`a`를 받아 각각 `b`와 `r`을 반환하는 함수 두 개만으로는 `b`를 받아 `r`을 반환하는 함수를 만들 방법이 전혀 없다! 첫 번째 함수를 어떻게든 뒤집어 `b`를 받아 `a`를 반환하게 만들 수 있다면 이야기가 달라질 것이다. 임의의 함수를 역으로 만들 수는 없지만 반대 범주로 갈 수는 있다.

짧게 복습하자. 모든 범주 *C*에는 쌍대 범주 *C<sup>op</sup>*가 있다. *C*와 객체는 같고 모든 화살표를 뒤집은 범주다.

*C<sup>op</sup>*에서 다른 범주 *D*로 가는 functor를 생각해 보자.
*F :: C<sup>op</sup> → D*
이 functor는 *C<sup>op</sup>*의 사상 *f<sup>op</sup> :: a → b*를 *D*의 사상 *F f<sup>op</sup> :: F a → F b*로 보낸다. 하지만 사상 *f<sup>op</sup>*는 사실 원래 범주 *C*의 어떤 사상 *f :: b → a*에 대응한다. 방향이 뒤집힌 것에 주목하자.

이제 *F*는 일반적인 functor지만, *F*를 바탕으로 functor가 아닌 다른 사상을 정의할 수 있다. 이를 *G*라고 하자. *C*에서 *D*로 가는 사상이다. 객체는 *F*와 같은 방식으로 보내지만 사상을 보낼 때는 방향을 뒤집는다. *C*의 사상 *f :: b → a*를 받아 먼저 반대 사상 *f<sup>op</sup> :: a → b*로 보낸 뒤, 여기에 functor F를 사용해 *F f<sup>op</sup> :: F a → F b*를 얻는다.

[![Contravariant](https://bartoszmilewski.files.wordpress.com/2015/01/contravariant.jpg?w=300&h=295)](https://bartoszmilewski.files.wordpress.com/2015/01/contravariant.jpg)

*F a*는 *G a*와 같고 *F b*는 *G b*와 같으므로 이 전체 여정은 다음처럼 나타낼 수 있다.
*G f :: (b → a) → (G a → G b)*
이는 "한 번 비튼 functor"다. 이런 방식으로 사상의 방향을 뒤집는 범주 사이 사상을 *반변 functor*라고 한다. 반변 functor는 반대 범주에서 출발하는 일반 functor일 뿐이라는 점에 주목하자. 한편 지금까지 공부한 종류의 일반 functor는 *공변 functor*라고 한다.

다음은 하스켈에서 반변 functor, 정확히는 반변 *endo*functor를 정의하는 타입 클래스다.

```haskell
class Contravariant f where
    contramap :: (b -> a) -> (f a -> f b)
```

타입 생성자 `Op`는 그 인스턴스다.

```haskell
instance Contravariant (Op r) where
    -- (b -> a) -> Op r a -> Op r b
    contramap f g = g . f
```

함수 `f`가 `Op`의 내용물인 함수 `g`의 *앞에*, 즉 오른쪽에 끼어든다는 점에 주목하자.

`Op`에 대한 `contramap` 정의는 인자를 뒤집은 함수 합성 연산자일 뿐임을 알아차리면 더 짧게 만들 수 있다. 인자를 뒤집는 `flip`이라는 특별한 함수가 있다.

```haskell
flip :: (a -> b -> c) -> (b -> a -> c)
flip f y x = f x y
```

이를 사용하면 다음과 같다.

```haskell
contramap = flip (.)
```

## Profunctor

함수 화살표 연산자는 첫 번째 인자에 대해 반변이고 두 번째 인자에 대해 공변임을 보았다. 이런 존재를 부르는 이름이 있을까? 대상 범주가 **Set**일 때 이런 존재를 *profunctor*라고 한다. 반변 functor는 반대 범주에서 출발하는 공변 functor와 동등하므로 profunctor는 다음과 같이 정의한다.
*C<sup>op</sup> × D → Set*

첫 번째 근사로 하스켈 타입을 집합으로 볼 수 있으므로, 인자 두 개를 받으며 첫 번째 인자에 대해서는 반변 functorial하고 두 번째 인자에 대해서는 functorial한 타입 생성자 `p`에 `Profunctor`라는 이름을 붙인다. 다음은 `Data.Profunctor` 라이브러리에서 가져온 타입 클래스다.

```haskell
class Profunctor p where
  dimap :: (a -> b) -> (c -> d) -> p b c -> p a d
  dimap f g = lmap f . rmap g
  lmap :: (a -> b) -> p b c -> p a c
  lmap f = dimap f id
  rmap :: (b -> c) -> p a b -> p a c
  rmap = dimap id
```

세 함수 모두 기본 구현이 있다. `Bifunctor`와 마찬가지로 `Profunctor` 인스턴스를 선언할 때는 `dimap`을 구현하고 `lmap`과 `rmap`의 기본 구현을 받아들이거나, `lmap`과 `rmap`을 모두 구현하고 `dimap`의 기본 구현을 받아들이는 방법 중 하나를 고를 수 있다.

![dimap](images/dimap.jpg)

이제 함수 화살표 연산자가 `Profunctor`의 인스턴스라고 단언할 수 있다.

```haskell
instance Profunctor (->) where
  dimap ab cd bc = cd . bc . ab
  lmap = flip (.)
  rmap = (.)
```

profunctor는 하스켈 lens 라이브러리에 응용된다. end와 coend를 이야기할 때 다시 만나게 될 것이다.

## 연습문제

1. 다음 데이터 타입이 bifunctor임을 보여라.
```haskell
data Pair a b = Pair a b
```
추가 점수를 얻으려면 `Bifunctor`의 세 메서드를 모두 구현하고 방정식 추론을 사용해, 적용할 수 있는 경우 이 정의들이 기본 구현과 양립함을 보여라.

2. `Maybe`의 표준 정의와 다음과 같이 문법을 풀어 쓴 정의 사이의 동형을 보여라.
```haskell
type Maybe' a = Either (Const () a) (Identity a)
```
힌트: 두 구현 사이의 사상 두 개를 정의하라. 추가 점수를 얻으려면 방정식 추론으로 두 사상이 서로의 역임을 보여라.

3. 다른 데이터 구조를 시도해 보자. 재귀를 타입 매개변수 `b`로 대체하므로 이를 `List`의 전신이라는 뜻에서 `PreList`라고 부르겠다.
```haskell
data PreList a b = Nil | Cons a b
```
`PreList`를 자기 자신에 재귀적으로 적용하면 앞서 정의한 `List`를 되찾을 수 있다. 고정점을 이야기할 때 그 방법을 보게 될 것이다.

`PreList`가 `Bifunctor`의 인스턴스임을 보여라.

4. 다음 데이터 타입들이 `a`와 `b`에 대해 bifunctor를 정의함을 보여라.
```haskell
data K2 c a b = K2 c
```
```haskell
data Fst a b = Fst a
```
```haskell
data Snd a b = Snd b
```
추가 점수를 얻으려면 Conor McBride의 논문 [Clowns to the Left of me, Jokers to the Right](http://strictlypositive.org/CJ.pdf)와 답을 대조하라.

5. 하스켈 이외의 언어로 bifunctor를 정의하라. 그 언어의 제네릭 쌍에 대해 `bimap`을 구현하라.

6. `std::map`은 두 템플릿 인자 `Key`와 `T`에 대해 bifunctor로 보아야 할까, profunctor로 보아야 할까? 그렇게 만들려면 이 데이터 타입을 어떻게 다시 설계해야 할까?
