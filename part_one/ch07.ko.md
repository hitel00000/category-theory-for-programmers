# Functor {#functors}

망가진 레코드처럼 같은 말을 반복하는 위험을 무릅쓰고 functor에 대해 이렇게 말하겠다. functor는 아주 단순하지만 강력한 아이디어다. 범주론에는 이런 단순하지만 강력한 아이디어가 가득하다. functor는 범주 사이의 사상이다. 두 범주 C와 D가 주어졌을 때, functor F는 C의 객체를 D의 객체로 보낸다. 즉 객체에 대한 함수다. *a*가 C의 객체라면, D에서의 그 이미지를 *F a*라고 쓰겠다. 괄호는 쓰지 않는다. 하지만 범주는 객체만으로 이루어진 것이 아니다. 객체들과 그 객체들을 잇는 사상들로 이루어진다. functor는 사상도 보낸다. 즉 사상에 대한 함수이기도 하다. 다만 사상을 제멋대로 보내지는 않는다. 연결 관계를 보존한다. 따라서 C의 사상 *f*가 객체 *a*를 객체 *b*에 연결한다면:

```haskell
f :: a -> b
```

D에서 *f*의 이미지인 *F f*는 *a*의 이미지와 *b*의 이미지를 연결한다.

```haskell
F f :: F a -> F b
```

이것은 수학 표기와 하스켈 표기가 섞인 것이지만, 이제는 의미가 통하기를 바란다. functor를 객체나 사상에 적용할 때는 괄호를 쓰지 않겠다.

![](images/functor.jpg)

보다시피 functor는 범주의 구조를 보존한다. 한 범주에서 연결되어 있는 것은 다른 범주에서도 연결되어 있다. 하지만 범주의 구조에는 더 많은 것이 있다. 사상의 합성도 있다. *h*가 *f*와 *g*의 합성이라면:

```haskell
h = g . f
```

F 아래에서의 그 이미지는 *f*와 *g*의 이미지의 합성이기를 원한다.

```haskell
F h = F g . F f
```

![](images/functorcompos.jpg)

마지막으로, C의 모든 항등 사상은 D의 항등 사상으로 보내져야 한다.

<pre>
F id<sub>a</sub> = id<sub>F a</sub>
</pre>

여기서 *id<sub>a</sub>*는 객체 *a*에서의 항등이고, *id<sub>F a</sub>*는 *F a*에서의 항등이다.

![](images/functorid.jpg)

이 조건들 때문에 functor는 일반 함수보다 훨씬 더 제한적이다. functor는 범주의 구조를 보존해야 한다. 범주를 사상들의 그물망으로 함께 붙들린 객체들의 모음으로 그려 본다면, functor는 그 직물에 찢어진 자국을 만들 수 없다. 여러 객체를 하나로 뭉갤 수 있고, 여러 사상을 하나로 붙일 수는 있지만, 무언가를 끊어 놓을 수는 없다. 이 찢지 않기 조건은 미적분에서 아는 연속성 조건과 비슷하다. 그런 의미에서 functor는 "연속적"이다. 물론 functor에 대해 더 엄격한 연속성 개념도 존재한다. 함수처럼 functor도 붕괴와 매장을 모두 할 수 있다. 원천 범주가 대상 범주보다 훨씬 작을 때는 매장하는 측면이 더 두드러진다. 극단적으로 원천은 사소한 한 원소 범주, 즉 객체 하나와 사상 하나(항등)만 가진 범주일 수 있다. 한 원소 범주에서 임의의 다른 범주로 가는 functor는 그 범주의 객체 하나를 고르는 것뿐이다. 이는 한 원소 집합에서 대상 집합으로 가는 사상이 대상 집합의 원소를 고르는 성질과 완전히 유사하다. 최대한 붕괴시키는 functor는 상수 functor Δ<sub>c</sub>라고 부른다. 이것은 원천 범주의 모든 객체를 대상 범주의 선택된 객체 *c*로 보낸다. 또한 원천 범주의 모든 사상을 항등 사상 *id<sub>c</sub>*로 보낸다. 마치 모든 것을 하나의 특이점으로 압축하는 블랙홀처럼 행동한다. 극한과 쌍대극한을 논의할 때 이 functor를 더 보게 될 것이다.

## 프로그래밍에서의 Functor

이제 땅으로 내려와 프로그래밍 이야기를 하자. 우리에게는 타입과 함수의 범주가 있다. 이 범주를 자기 자신으로 보내는 functor를 이야기할 수 있다. 이런 functor를 endofunctor라고 부른다. 그렇다면 타입의 범주에서 endofunctor란 무엇인가? 우선 타입을 타입으로 보낸다. 우리는 이미 그런 사상의 예를 보았다. 어쩌면 그것이 바로 그런 것이라는 사실을 깨닫지 못했을 수도 있다. 다른 타입으로 매개변수화된 타입 정의를 말하는 것이다. 몇 가지 예를 보자.

### Maybe Functor

`Maybe`의 정의는 타입 `a`를 타입 `Maybe a`로 보내는 사상이다.

```haskell
data Maybe a = Nothing | Just a
```

중요한 미묘함이 있다. `Maybe` 자체는 타입이 아니다. *타입 생성자*다. `Int`나 `Bool` 같은 타입 인자를 주어야 타입이 된다. 인자가 없는 `Maybe`는 타입 위의 함수를 나타낸다. 그런데 `Maybe`를 functor로 만들 수 있을까? 이제부터 프로그래밍 맥락에서 functor라고 말할 때는 거의 항상 endofunctor를 뜻한다. functor는 객체, 여기서는 타입, 의 사상일 뿐 아니라 사상, 여기서는 함수, 의 사상이기도 하다. 임의의 함수:

```haskell
f :: a -> b
```

가 있을 때, 우리는 `Maybe a`에서 `Maybe b`로 가는 함수를 만들고 싶다. 그런 함수를 정의하려면 `Maybe`의 두 생성자에 대응하는 두 경우를 고려해야 한다. `Nothing`의 경우는 단순하다. 그냥 `Nothing`을 돌려주면 된다. 인자가 `Just`라면 그 안의 내용에 함수 `f`를 적용한다. 따라서 `Maybe` 아래에서 `f`의 이미지는 다음 함수다.

```haskell
f' :: Maybe a -> Maybe b
f' Nothing = Nothing
f' (Just x) = Just (f x)
```

참고로 하스켈에서는 변수 이름에 아포스트로피를 사용할 수 있어서 이런 경우에 아주 편리하다. 하스켈에서는 functor의 사상 사상 부분을 `fmap`이라는 고차 함수로 구현한다. `Maybe`의 경우 그 시그니처는 다음과 같다.

```haskell
fmap :: (a -> b) -> (Maybe a -> Maybe b)
```

![](images/functormaybe.jpg)

우리는 종종 `fmap`이 함수를 *끌어올린다*고 말한다. 끌어올려진 함수는 `Maybe` 값에 작용한다. 늘 그렇듯 커링 때문에 이 시그니처는 두 방식으로 해석할 수 있다. 하나는 한 인자, 그 자체가 함수 `(a->b)`인 인자를 받아 함수 `(Maybe a -> Maybe b)`를 반환하는 함수로 보는 것이다. 다른 하나는 두 인자를 받아 `Maybe b`를 반환하는 함수로 보는 것이다.

```haskell
fmap :: (a -> b) -> Maybe a -> Maybe b
```

앞의 논의를 바탕으로 `Maybe`에 대한 `fmap`은 다음처럼 구현한다.

```haskell
fmap _ Nothing = Nothing
fmap f (Just x) = Just (f x)
```

타입 생성자 `Maybe`와 함수 `fmap`이 functor를 이룬다는 것을 보이려면, `fmap`이 항등과 합성을 보존한다는 것을 증명해야 한다. 이를 functor 법칙이라고 부르지만, 결국 범주의 구조 보존을 보장하는 조건일 뿐이다.

### 방정식 추론

functor 법칙을 증명하기 위해 나는 하스켈에서 흔히 쓰는 증명 기법인 *방정식 추론*을 사용할 것이다. 이 기법은 하스켈 함수가 등식으로 정의된다는 사실을 이용한다. 왼쪽은 오른쪽과 같다. 이름 충돌을 피하기 위해 변수를 바꾸기만 하면 언제든 한쪽을 다른 쪽으로 대체할 수 있다. 이것을 함수 인라인으로 생각해도 되고, 반대로 표현식을 함수로 리팩터링하는 것으로 생각해도 된다. 항등 함수를 예로 들자.

```haskell
id x = x
```

어떤 표현식에서 `id y`를 보면 그것을 `y`로 바꿀 수 있다. 인라인이다. 더 나아가 `id`가 어떤 표현식에 적용된 것을 보면, 예를 들어 `id (y + 2)`를 보면 그 표현식 자체 `(y + 2)`로 바꿀 수 있다. 이 치환은 양방향으로 작동한다. 임의의 표현식 `e`를 `id e`로 바꿀 수도 있다. 리팩터링이다. 함수가 패턴 매칭으로 정의되어 있다면 각 부분 정의를 독립적으로 사용할 수 있다. 예를 들어 위의 `fmap` 정의가 주어졌다면 `fmap f Nothing`을 `Nothing`으로 바꿀 수 있고, 그 반대도 가능하다. 실제로 어떻게 작동하는지 보자. 항등 보존부터 시작하자.

```haskell
fmap id = id
```

두 경우를 고려해야 한다. `Nothing`과 `Just`다. 첫 번째 경우는 다음과 같다. 왼쪽을 오른쪽으로 바꾸기 위해 하스켈식 의사 코드를 사용한다.

```haskell
  fmap id Nothing 
= { definition of fmap }
  Nothing 
= { definition of id }
  id Nothing
```

마지막 단계에서 `id`의 정의를 거꾸로 사용했다는 점에 주목하자. 표현식 `Nothing`을 `id Nothing`으로 바꾸었다. 실제로 이런 증명은 "양쪽 끝에서 촛불을 태우듯" 수행하다가 가운데에서 같은 표현식을 만나면 된다. 여기서는 그것이 `Nothing`이었다. 두 번째 경우도 쉽다.

```haskell
  fmap id (Just x) 
= { definition of fmap }
  Just (id x) 
= { definition of id }
  Just x
= { definition of id }
  id (Just x)
```

이제 `fmap`이 합성을 보존한다는 것을 보이자.

```haskell
fmap (g . f) = fmap g . fmap f
```

먼저 `Nothing`의 경우다.

```haskell
  fmap (g . f) Nothing 
= { definition of fmap }
  Nothing 
= { definition of fmap }
  fmap g Nothing
= { definition of fmap }
  fmap g (fmap f Nothing)
```

그리고 `Just`의 경우다.

```haskell
  fmap (g . f) (Just x)
= { definition of fmap }
  Just ((g . f) x)
= { definition of composition }
  Just (g (f x))
= { definition of fmap }
  fmap g (Just (f x))
= { definition of fmap }
  fmap g (fmap f (Just x))
= { definition of composition }
  (fmap g . fmap f) (Just x)
```

방정식 추론은 부수 효과가 있는 C++식 "함수"에는 작동하지 않는다는 점을 강조할 가치가 있다. 다음 코드를 보자.

```cpp
int square(int x) {
    return x * x;
}

int counter() {
    static int c = 0;
    return c++;
}

double y = square(counter());
```

방정식 추론을 사용하면 `square`를 인라인해 다음을 얻을 수 있을 것이다.

```cpp
double y = counter() * counter();
```

이것은 절대로 유효한 변환이 아니며 같은 결과를 만들지 않는다. 그런데도 C++ 컴파일러는 `square`를 매크로로 구현하면 방정식 추론을 시도할 것이고, 결과는 참담할 수 있다.

### Optional

functor는 하스켈에서 쉽게 표현되지만, 제네릭 프로그래밍과 고차 함수를 지원하는 어떤 언어에서도 정의할 수 있다. `Maybe`의 C++ 유사물인 템플릿 타입 `optional`을 생각해 보자. 구현의 개략은 다음과 같다. 실제 구현은 훨씬 복잡하다. 인자가 전달되는 여러 방식, 복사 의미론, C++ 특유의 자원 관리 문제를 다뤄야 하기 때문이다.

```cpp
template<class T>
class optional {
    bool _isValid; // the tag
    T    _v;
public:
    optional()    : _isValid(false) {}         // Nothing
    optional(T x) : _isValid(true) , _v(x) {}  // Just
    bool isValid() const { return _isValid; }
    T val() const { return _v; }
};
```

이 템플릿은 functor 정의의 한 부분, 즉 타입의 사상을 제공한다. 임의의 타입 `T`를 새 타입 `optional<T>`로 보낸다. 이제 함수에 대한 작용을 정의하자.

```cpp
template<class A, class B>
std::function<optional<B>(optional<A>)> 
fmap(std::function<B(A)> f) 
{
    return [f](optional<A> opt) {
        if (!opt.isValid())
            return optional<B>{};
        else
            return optional<B>{ f(opt.val()) };
    };
}
```

이것은 함수를 인자로 받아 함수를 반환하는 고차 함수다. 커리하지 않은 버전은 다음과 같다.

```cpp
template<class A, class B>
optional<B> fmap(std::function<B(A)> f, optional<A> opt) {
    if (!opt.isValid())
        return optional<B>{};
    else
        return optional<B>{ f(opt.val()) };
}
```

`fmap`을 `optional`의 템플릿 메서드로 만드는 선택지도 있다. 선택지가 이렇게 많다는 사실이 C++에서 functor 패턴을 추상화하는 일을 문제로 만든다. functor는 상속할 인터페이스여야 할까? 안타깝게도 템플릿 가상 함수는 가질 수 없다. 커리된 자유 템플릿 함수여야 할까, 아니면 커리하지 않은 자유 템플릿 함수여야 할까? C++ 컴파일러가 빠진 타입을 올바르게 추론할 수 있을까, 아니면 명시해야 할까? 입력 함수 `f`가 `int`를 `bool`로 보낸다고 하자. 컴파일러는 다음에서 `g`의 타입을 어떻게 알아낼까?

```cpp
auto g = fmap(f);
```

특히 나중에 여러 functor가 `fmap`을 오버로드하게 된다면 말이다. 곧 더 많은 functor를 보게 될 것이다.

### Typeclass

그렇다면 하스켈은 functor 추상화를 어떻게 다룰까? 타입클래스 메커니즘을 사용한다. 타입클래스는 공통 인터페이스를 지원하는 타입들의 가족을 정의한다. 예를 들어 동등성을 지원하는 객체들의 클래스는 다음처럼 정의된다.

```haskell
class Eq a where
    (==) :: a -> a -> Bool
```

이 정의는 타입 `a`가 타입 `a`의 두 인자를 받아 `Bool`을 반환하는 연산자 `(==)`를 지원한다면 `Eq` 클래스에 속한다는 뜻이다. 특정 타입이 `Eq`라고 하스켈에 알려 주려면, 그 타입을 이 클래스의 *인스턴스*로 선언하고 `(==)` 구현을 제공해야 한다. 예를 들어 2차원 `Point`, 즉 두 `Float`의 곱 타입이 다음처럼 정의되어 있다고 하자.

```haskell
data Point = Pt Float Float
```

점의 동등성을 다음처럼 정의할 수 있다.

```haskell
instance Eq Point where
    (Pt x y) == (Pt x' y') = x == x' && y == y'
```

여기서 나는 정의하고 있는 연산자 `(==)`를 두 패턴 `(Pt x y)`와 `(Pt x' y')` 사이의 중위 위치에 사용했다. 함수 본문은 하나의 등호 뒤에 온다. `Point`가 `Eq`의 인스턴스로 선언되면, 점들을 직접 동등성으로 비교할 수 있다. C++나 Java와 달리 `Point`를 정의할 때 `Eq` 클래스, 또는 인터페이스를 지정할 필요가 없다는 점에 주목하자. 나중에 클라이언트 코드에서 할 수 있다. 타입클래스는 하스켈에서 함수와 연산자를 오버로드하는 유일한 메커니즘이기도 하다. 서로 다른 functor에 대해 `fmap`을 오버로드하려면 이것이 필요하다. 다만 한 가지 복잡함이 있다. functor는 타입으로 정의되는 것이 아니라 타입의 사상, 즉 타입 생성자로 정의된다. 따라서 `Eq`의 경우처럼 타입들의 가족이 아니라 타입 생성자들의 가족인 타입클래스가 필요하다. 다행히 하스켈 타입클래스는 타입뿐 아니라 타입 생성자에도 작동한다. `Functor` 클래스의 정의는 다음과 같다.

```haskell
class Functor f where
    fmap :: (a -> b) -> f a -> f b
```

이는 지정된 타입 시그니처를 가진 함수 `fmap`이 존재하면 `f`가 `Functor`라는 뜻이다. 소문자 `f`는 타입 변수이며, 타입 변수 `a`와 `b`와 비슷하다. 하지만 컴파일러는 사용 방식을 보고 그것이 타입이 아니라 타입 생성자를 나타낸다는 것을 추론할 수 있다. `f a`와 `f b`처럼 다른 타입에 작용하고 있기 때문이다. 따라서 `Functor`의 인스턴스를 선언할 때는 `Maybe`의 경우처럼 타입 생성자를 제공해야 한다.

```haskell
instance Functor Maybe where
    fmap _ Nothing = Nothing
    fmap f (Just x) = Just (f x)
```

참고로 `Functor` 클래스와, `Maybe`를 포함한 많은 단순 데이터 타입에 대한 그 인스턴스 정의는 표준 Prelude 라이브러리의 일부다.

### C++의 Functor

C++에서도 같은 접근을 시도할 수 있을까? 타입 생성자는 `optional` 같은 템플릿 클래스에 대응하므로, 유추에 따라 `fmap`을 *템플릿 템플릿 매개변수* `F`로 매개변수화할 것이다. 문법은 다음과 같다.

```cpp
template<template<class> F, class A, class B>
F<B> fmap(std::function<B(A)>, F<A>);
```

우리는 이 템플릿을 서로 다른 functor에 대해 특수화할 수 있기를 원한다. 안타깝게도 C++에서는 템플릿 함수의 부분 특수화가 금지되어 있다. 다음처럼 쓸 수 없다.

```cpp
template<class A, class B>
optional<B> fmap<optional>(std::function<B(A)> f, optional<A> opt)
```

대신 함수 오버로드에 의존해야 하고, 이는 우리를 커리하지 않은 `fmap`의 원래 정의로 되돌린다.

```cpp
template<class A, class B>
optional<B> fmap(std::function<B(A)> f, optional<A> opt) 
{
    if (!opt.isValid())
        return optional<B>{};
    else
        return optional<B>{ f(opt.val()) };
}
```

이 정의는 작동하지만, `fmap`의 두 번째 인자가 오버로드를 선택하기 때문에만 작동한다. 더 일반적인 `fmap` 정의는 완전히 무시된다.

### List Functor

프로그래밍에서 functor가 어떤 역할을 하는지 직관을 얻으려면 더 많은 예를 보아야 한다. 다른 타입으로 매개변수화된 어떤 타입이든 functor의 후보가 된다. 제네릭 컨테이너는 저장하는 원소의 타입으로 매개변수화되므로, 아주 단순한 컨테이너인 리스트를 보자.

```haskell
data List a = Nil | Cons a (List a)
```

타입 생성자 `List`가 있고, 이것은 임의의 타입 `a`를 타입 `List a`로 보내는 사상이다. `List`가 functor임을 보이려면 함수의 끌어올림을 정의해야 한다. 함수 `a->b`가 주어졌을 때 함수 `List a -> List b`를 정의하는 것이다.

```haskell
fmap :: (a -> b) -> (List a -> List b)
```

`List a`에 작용하는 함수는 두 리스트 생성자에 대응하는 두 경우를 고려해야 한다. `Nil`의 경우는 사소하다. 그냥 `Nil`을 반환하면 된다. 빈 리스트로 할 수 있는 일은 별로 없다. `Cons`의 경우는 재귀가 포함되므로 조금 까다롭다. 잠시 한 걸음 물러서서 우리가 하려는 일을 생각해 보자. `a`의 리스트와 `a`를 `b`로 바꾸는 함수 `f`가 있고, 우리는 `b`의 리스트를 만들고 싶다. 당연한 방법은 `f`를 사용해 리스트의 각 원소를 `a`에서 `b`로 바꾸는 것이다. 비어 있지 않은 리스트가 머리와 꼬리의 `Cons`로 정의되어 있을 때 이를 실제로 어떻게 할까? 머리에는 `f`를 적용하고, 꼬리에는 끌어올린, 즉 `fmap`된 `f`를 적용한다. 이는 끌어올린 `f`를 끌어올린 `f` 자신으로 정의하는 재귀적 정의다.

```haskell
fmap f (Cons x t) = Cons (f x) (fmap f t)
```

오른쪽에서 `fmap f`가 우리가 정의하고 있는 리스트보다 더 짧은 리스트, 즉 그 꼬리에 적용된다는 점에 주목하자. 우리는 점점 더 짧은 리스트로 재귀하므로 결국 빈 리스트, 즉 `Nil`에 도달하게 된다. 앞서 정했듯이 `Nil`에 작용하는 `fmap f`는 `Nil`을 반환하므로 재귀가 종료된다. 최종 결과를 얻기 위해 새 머리 `(f x)`와 새 꼬리 `(fmap f t)`를 `Cons` 생성자로 결합한다. 모두 합치면 리스트 functor의 인스턴스 선언은 다음과 같다.

```haskell
instance Functor List where
    fmap _ Nil = Nil
    fmap f (Cons x t) = Cons (f x) (fmap f t)
```

C++가 더 편하다면 가장 일반적인 C++ 컨테이너라고 볼 수 있는 `std::vector`의 경우를 생각해 보자. `std::vector`에 대한 `fmap` 구현은 `std::transform`을 얇게 감싼 것에 불과하다.

```cpp
template<class A, class B>
std::vector<B> fmap(std::function<B(A)> f, std::vector<A> v)
{
    std::vector<B> w;
    std::transform( std::begin(v)
                  , std::end(v)
                  , std::back_inserter(w)
                  , f);
    return w;
}
```

예를 들어 숫자 시퀀스의 원소를 제곱하는 데 사용할 수 있다.

```cpp
std::vector<int> v{ 1, 2, 3, 4 };
auto w = fmap([](int i) { return i*i; }, v);
std::copy( std::begin(w)
         , std::end(w)
         , std::ostream_iterator(std::cout, ", "));
```

대부분의 C++ 컨테이너는 `std::transform`에 넘길 수 있는 반복자를 구현한다는 점에서 functor다. `std::transform`은 `fmap`의 더 원시적인 사촌이다. 안타깝게도 functor의 단순함은 반복자와 임시 객체의 일반적인 소음 속에 묻힌다. 위의 `fmap` 구현을 보라. 새로 제안된 C++ range 라이브러리가 range의 functor적 성질을 훨씬 더 뚜렷하게 만든다는 점은 반갑다.

### Reader Functor

이제 functor가 어떤 종류의 컨테이너라는 직관이 어느 정도 생겼을 수 있다. 처음 보기에는 매우 달라 보이는 예를 하나 보여 주겠다. 타입 `a`를 `a`를 반환하는 함수 타입으로 보내는 사상을 생각해 보자. 우리는 함수 타입을 깊이 다루지는 않았다. 완전한 범주론적 처리는 나중에 올 것이다. 하지만 프로그래머로서 함수 타입에 대한 이해는 어느 정도 있다. 하스켈에서 함수 타입은 화살표 타입 생성자 `(->)`를 사용해 만들어진다. 이 생성자는 두 타입, 인자 타입과 결과 타입을 받는다. 이미 중위 형태 `a->b`로 보았지만, 괄호로 감싸면 전위 형태로도 사용할 수 있다.

```haskell
(->) a b
```

일반 함수와 마찬가지로 인자가 둘 이상인 타입 함수도 부분 적용될 수 있다. 그래서 화살표에 타입 인자를 하나만 제공하면, 여전히 다른 하나를 기대한다. 따라서:

```haskell
(->) a
```

는 타입 생성자다. 완전한 타입 `a->b`를 만들려면 타입 `b`가 하나 더 필요하다. 이 상태로는 `a`로 매개변수화된 타입 생성자들의 온 가족을 정의한다. 이것도 functor들의 가족인지 보자. 두 타입 매개변수를 다루면 조금 헷갈릴 수 있으므로 이름을 바꾸자. 이전 functor 정의와 맞춰 인자 타입을 `r`, 결과 타입을 `a`라고 부르자. 그러면 우리의 타입 생성자는 임의의 타입 `a`를 타입 `r->a`로 보낸다. 이것이 functor임을 보이려면 함수 `a->b`를 `r->a`를 받아 `r->b`를 반환하는 함수로 끌어올리고 싶다. 이 타입들은 타입 생성자 `(->) r`이 각각 `a`와 `b`에 작용해 만들어진다. 이 경우에 적용된 `fmap`의 타입 시그니처는 다음과 같다.

```haskell
fmap :: (a -> b) -> (r -> a) -> (r -> b)
```

우리는 다음 퍼즐을 풀어야 한다. 함수 `f::a->b`와 함수 `g::r->a`가 주어졌을 때 함수 `r->b`를 만들어라. 두 함수를 합성할 수 있는 방법은 하나뿐이고, 그 결과가 정확히 우리가 필요로 하는 것이다. 따라서 `fmap` 구현은 다음과 같다.

```haskell
instance Functor ((->) r) where
    fmap f g = f . g
```

그냥 작동한다. 간결한 표기를 좋아한다면, 합성을 전위 형태로 다시 쓸 수 있다는 점을 이용해 이 정의를 더 줄일 수 있다.

```haskell
fmap f g = (.) f g
```

그리고 인자를 생략해 두 함수의 직접 동등성으로 만들 수 있다.

```haskell
fmap = (.)
```

타입 생성자 `(->) r`와 위의 `fmap` 구현의 조합을 reader functor라고 부른다.

## 컨테이너로서의 Functor

우리는 범용 컨테이너, 또는 적어도 매개변수화된 타입의 어떤 값을 담는 객체를 정의하는 프로그래밍 언어의 functor 예를 몇 가지 보았다. reader functor는 함수가 데이터라고 생각하지 않기 때문에 예외처럼 보인다. 하지만 순수 함수는 메모화될 수 있고, 함수 실행은 테이블 조회로 바뀔 수 있다는 것을 보았다. 테이블은 데이터다. 반대로 하스켈의 게으른 평가 때문에 리스트 같은 전통적인 컨테이너가 실제로는 함수로 구현될 수도 있다. 예를 들어 자연수의 무한 리스트는 다음처럼 간결하게 정의할 수 있다.

```haskell
nats :: [Integer]
nats = [1..]
```

첫 줄에서 대괄호 쌍은 하스켈의 내장 리스트 타입 생성자다. 둘째 줄에서 대괄호는 리스트 리터럴을 만드는 데 쓰인다. 이런 무한 리스트는 당연히 메모리에 저장될 수 없다. 컴파일러는 필요할 때 `Integer`를 생성하는 함수로 구현한다. 하스켈은 데이터와 코드의 구분을 사실상 흐릿하게 만든다. 리스트는 함수로 볼 수 있고, 함수는 인자를 결과로 보내는 테이블로 볼 수 있다. 후자는 함수의 정의역이 유한하고 그리 크지 않다면 실제로도 유용할 수 있다. 하지만 문자열은 무한히 많으므로 `strlen`을 테이블 조회로 구현하는 것은 실용적이지 않을 것이다. 프로그래머로서 우리는 무한을 좋아하지 않지만, 범주론을 배우면 무한을 아침 식사처럼 먹게 된다. 모든 문자열의 집합이든, 우주의 과거와 현재와 미래의 가능한 모든 상태의 모음이든, 우리는 다룰 수 있다. 그래서 나는 functor 객체, 즉 endofunctor가 생성한 타입의 객체를 그것이 매개변수화된 타입의 값 또는 값들을 담고 있는 것으로 생각하기를 좋아한다. 그 값들이 물리적으로 그 안에 존재하지 않더라도 말이다. functor의 한 예는 C++의 `std::future`다. 어느 시점에는 값을 담을 수 있지만, 반드시 그렇다는 보장은 없다. 그 값을 접근하려면 다른 스레드가 실행을 마치기를 기다리며 블록될 수도 있다. 또 다른 예는 하스켈의 `IO` 객체다. 사용자 입력을 담고 있을 수도 있고, 모니터에 "Hello World!"가 표시된 우리 우주의 미래 버전을 담고 있을 수도 있다. 이 해석에 따르면 functor 객체는 매개변수화된 타입의 값 또는 값들을 담을 수 있는 무엇이다. 또는 그런 값들을 생성하는 조리법을 담을 수도 있다. 우리는 그 값들에 접근할 수 있는지에는 전혀 관심이 없다. 그것은 완전히 선택 사항이며 functor의 범위 밖이다. 우리가 관심 있는 것은 함수를 사용해 그 값들을 조작할 수 있다는 점뿐이다. 값들에 접근할 수 있다면 이 조작의 결과를 볼 수 있어야 한다. 접근할 수 없다면 조작들이 올바르게 합성되고, 항등 함수로 조작해도 아무것도 바뀌지 않는다는 사실만 중요하다. functor 객체 안의 값에 접근할 수 있는지에 우리가 얼마나 관심이 없는지 보여 주기 위해, 타입 인자 `a`를 완전히 무시하는 타입 생성자를 보자.

```haskell
data Const c a = Const c
```

`Const` 타입 생성자는 두 타입 `c`와 `a`를 받는다. 화살표 생성자에서 했던 것처럼, 이를 부분 적용해 functor를 만들 것이다. 데이터 생성자, 역시 `Const`라고 부른다, 는 타입 `c`의 값 하나만 받는다. `a`에는 전혀 의존하지 않는다. 이 타입 생성자에 대한 `fmap`의 타입은 다음과 같다.

```haskell
fmap :: (a -> b) -> Const c a -> Const c b
```

functor가 타입 인자를 무시하므로, `fmap` 구현은 함수 인자를 자유롭게 무시할 수 있다. 그 함수가 작용할 대상이 없기 때문이다.

```haskell
instance Functor (Const c) where
    fmap _ (Const v) = Const v
```

C++에서는 이 점이 조금 더 분명할 수도 있다. 내가 이런 말을 하게 될 줄은 몰랐다. C++에는 컴파일 시점의 타입 인자와 실행 시점의 값 사이에 더 강한 구분이 있기 때문이다.

```cpp
template<class C, class A>
struct Const {
    Const(C v) : _v(v) {}
    C _v;
};
```

C++의 `fmap` 구현도 함수 인자를 무시하고, 본질적으로 `Const` 인자를 값은 바꾸지 않은 채 다시 캐스팅한다.

```cpp
template<class C, class A, class B>
Const<C, B> fmap(std::function<B(A)> f, Const<C, A> c) {
    return Const<C, B>{c._v};
}
```

이상해 보이지만 `Const` functor는 많은 구성에서 중요한 역할을 한다. 범주론에서는 앞서 언급한 Δ<sub>c</sub> functor의 특수한 경우다. 블랙홀의 endofunctor 버전이다. 앞으로 더 보게 될 것이다.

## Functor 합성

범주 사이의 functor가 집합 사이의 함수처럼 합성된다는 것은 어렵지 않게 납득할 수 있다. 두 functor의 합성이 객체에 작용할 때는 각각의 객체 사상의 합성일 뿐이고, 사상에 작용할 때도 마찬가지다. 두 functor를 통과한 항등 사상은 항등 사상으로 끝나고, 사상의 합성은 사상의 합성으로 끝난다. 특별히 복잡할 것이 없다. 특히 endofunctor는 쉽게 합성된다. `maybeTail` 함수를 기억하는가? 하스켈의 내장 리스트 구현을 사용해 다시 쓰겠다.

```haskell
maybeTail :: [a] -> Maybe [a]
maybeTail [] = Nothing
maybeTail (x:xs) = Just xs
```

우리가 `Nil`이라고 부르던 빈 리스트 생성자는 빈 대괄호 쌍 `[]`로 바뀐다. `Cons` 생성자는 중위 연산자 `:`(콜론)으로 바뀐다. `maybeTail`의 결과 타입은 `Maybe`와 `[]`라는 두 functor가 `a`에 작용한 합성이다. 각 functor에는 자기 나름의 `fmap` 버전이 있다. 그런데 어떤 함수 `f`를 합성된 것, 즉 `Maybe` 리스트의 내용에 적용하고 싶다면 어떻게 해야 할까? functor 층을 두 겹 뚫고 들어가야 한다. 바깥 `Maybe`를 뚫기 위해 `fmap`을 사용할 수 있다. 하지만 `f`를 그대로 `Maybe` 안으로 보낼 수는 없다. `f`는 리스트에 작용하지 않기 때문이다. 안쪽 리스트에 작용하도록 `(fmap f)`를 보내야 한다. 예를 들어 정수의 `Maybe` 리스트 안 원소들을 제곱하는 방법을 보자.

```haskell
square x = x * x

mis :: Maybe [Int]
mis = Just [1, 2, 3]

mis2 = fmap (fmap square) mis
```

컴파일러는 타입을 분석한 뒤 바깥 `fmap`에는 `Maybe` 인스턴스의 구현을, 안쪽 `fmap`에는 리스트 functor 구현을 사용해야 한다는 것을 알아낼 것이다. 위 코드가 다음처럼 다시 쓰일 수 있다는 점은 즉시 분명하지 않을 수도 있다.

```haskell
mis2 = (fmap . fmap) square mis
```

하지만 `fmap`을 인자 하나만 받는 함수로 볼 수 있다는 것을 기억하자.

```haskell
fmap :: (a -> b) -> (f a -> f b)
```

우리의 경우 `(fmap . fmap)`에서 두 번째 `fmap`은 다음을 인자로 받는다.

```haskell
square :: Int -> Int
```

그리고 다음 타입의 함수를 반환한다.

```haskell
[Int] -> [Int]
```

첫 번째 `fmap`은 그 함수를 받아 다음 함수를 반환한다.

```haskell
Maybe [Int] -> Maybe [Int]
```

마지막으로 그 함수가 `mis`에 적용된다. 따라서 두 functor의 합성은 functor이며, 그 `fmap`은 대응하는 `fmap`들의 합성이다. 범주론으로 돌아가면, functor 합성이 결합적이라는 것은 꽤 분명하다. 객체 사상이 결합적이고, 사상 사상도 결합적이다. 또한 모든 범주에는 사소한 항등 functor가 있다. 모든 객체를 자기 자신으로, 모든 사상을 자기 자신으로 보낸다. 그러므로 functor는 어떤 범주 안의 사상과 같은 모든 성질을 가진다. 그런데 그것은 어떤 범주일까? 객체가 범주이고 사상이 functor인 범주여야 한다. 범주의 범주다. 하지만 *모든* 범주의 범주는 자기 자신을 포함해야 하므로, 모든 집합의 집합을 불가능하게 만든 것과 같은 종류의 역설에 빠진다. 다만 모든 *작은* 범주의 범주인 **Cat**은 있다. **Cat**은 크기 때문에 자기 자신의 원소가 될 수 없다. 작은 범주는 객체들이 집합을 이루는 범주다. 집합보다 더 큰 것을 이루는 경우와 대비된다. 범주론에서는 무한 비가산 집합조차 "작다"고 여긴다는 점을 기억하라. 여러 추상화 수준에서 같은 구조가 반복되는 것을 알아볼 수 있다는 사실이 꽤 놀랍기 때문에 이런 이야기를 언급해 두고 싶었다. 나중에 functor들도 범주를 이룬다는 것을 보게 될 것이다.

## 연습문제

1. 다음처럼 두 인자를 모두 무시하는 정의로 `Maybe` 타입 생성자를 functor로 만들 수 있는가?
```haskell
fmap _ _ = Nothing
```
힌트: functor 법칙을 확인하라.

2. reader functor에 대해 functor 법칙을 증명하라. 힌트: 정말 간단하다.

3. 두 번째로 좋아하는 언어로 reader functor를 구현하라. 첫 번째는 물론 하스켈이다.

4. 리스트 functor에 대해 functor 법칙을 증명하라. 적용하는 리스트의 꼬리 부분에 대해서는 법칙이 참이라고 가정하라. 다시 말해 *귀납법*을 사용하라.
