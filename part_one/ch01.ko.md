# 범주: 합성의 본질 {#category-the-essence-of-composition}

> 이전 글인 [프로그래머를 위한 범주론 서문](../preface.ko.md)에 보내 주신 긍정적인 반응에 압도되었다. 동시에 사람들이 내게 얼마나 큰 기대를 걸고 있는지 깨닫고 몹시 겁이 나기도 했다. 내가 무엇을 쓰든 많은 독자가 실망할까 봐 걱정된다. 어떤 독자는 이 책이 더 실용적이기를 바랄 것이고, 어떤 독자는 더 추상적이기를 바랄 것이다. 어떤 사람은 C++를 싫어해서 모든 예제가 하스켈이기를 원하고, 또 어떤 사람은 하스켈을 싫어해서 자바 예제를 요구할 것이다. 설명 속도 역시 어떤 사람에게는 너무 느리고, 어떤 사람에게는 너무 빠를 것임을 안다. 이 책은 완벽한 책이 되지는 못할 것이다. 타협의 산물이 될 것이다. 내가 바랄 수 있는 것은 독자들과 내 몇몇 깨달음의 순간을 나눌 수 있기를 바라는 것뿐이다. 기본부터 시작해 보자.

범주는 민망할 정도로 단순한 개념이다. 범주는 객체와 그 객체들 사이를 잇는 화살표로 이루어진다. 그래서 범주는 그림으로 표현하기가 아주 쉽다. 객체는 원이나 점으로 그릴 수 있고, 화살표는 말 그대로 화살표다. (가끔 변화를 주려고 객체를 돼지로, 화살표를 폭죽으로 그리기도 할 것이다.) 하지만 범주의 본질은 합성이다. 혹은 이렇게 말해도 좋다. 합성의 본질이 범주다. 화살표는 합성된다. 객체 A에서 객체 B로 가는 화살표가 있고, 객체 B에서 객체 C로 가는 또 다른 화살표가 있다면, A에서 C로 가는 화살표, 즉 이 둘의 합성이 반드시 있어야 한다.

![범주에서 A에서 B로 가는 화살표와 B에서 C로 가는 화살표가 있다면, 그 합성인 A에서 C로 가는 직접 화살표도 반드시 있어야 한다. 이 그림은 항등 사상이 빠져 있으므로 완전한 범주는 아니다. 항등 사상은 뒤에서 설명한다.](images/img_1330.jpg)

## 함수로서의 화살표

벌써 너무 추상적인 헛소리처럼 느껴지는가? 절망하지 말자. 구체적인 이야기를 해 보자. 사상이라고도 부르는 화살표를 함수라고 생각하자. 타입 A의 인자를 받아 B를 반환하는 함수 f가 있다. 또 B를 받아 C를 반환하는 함수 g가 있다. f의 결과를 g에 넘기면 두 함수를 합성할 수 있다. 그러면 A를 받아 C를 반환하는 새 함수를 정의한 셈이다.

수학에서는 이런 합성을 함수 사이에 작은 원을 넣어 `g ∘ f`처럼 표기한다. 합성의 순서가 오른쪽에서 왼쪽이라는 점에 주의하자. 어떤 사람에게는 이 점이 헷갈린다. 유닉스의 파이프 표기법에 익숙할 수도 있다. 예를 들면 다음과 같다.

```bash
lsof | grep Chrome
```

또는 F#의 꺾쇠 `>>`처럼 왼쪽에서 오른쪽으로 흐르는 표기법도 있다. 하지만 수학과 하스켈에서는 함수가 오른쪽에서 왼쪽으로 합성된다. `g ∘ f`를 "`f` 다음에 `g`"라고 읽으면 도움이 된다.

이제 C 코드로 좀 더 명확히 써 보자. 타입 A의 인자를 받아 타입 B의 값을 반환하는 함수 f가 있다.

```haskell
B f(A a);
```

그리고 또 다른 함수가 있다.

```haskell
C g(B b);
```

이 둘의 합성은 다음과 같다.

```cpp
C g_after_f(A a)
{
    return g(f(a));
}
```

여기서도 다시 오른쪽에서 왼쪽으로의 합성이 보인다. 이번에는 C에서 `g(f(a))`라고 쓴 것이다.

C++ 표준 라이브러리에 두 함수를 받아 그 합성을 반환하는 템플릿이 있다고 말할 수 있으면 좋겠지만, 그런 것은 없다. 그러니 기분 전환 삼아 하스켈을 조금 써 보자. A에서 B로 가는 함수의 선언은 다음과 같다.

```haskell
f :: A -> B
```

마찬가지로 다음과 같다.

```haskell
g :: B -> C
```

이 둘의 합성은 다음과 같다.

```haskell
g . f
```

하스켈에서는 일이 얼마나 단순한지 보고 나면, C++에서 이런 곧바른 함수형 개념을 표현하기 어렵다는 사실이 조금 민망해진다. 실제로 하스켈에서는 유니코드 문자를 사용할 수 있으므로 합성을 다음처럼 쓸 수도 있다.

```haskell
g ∘ f
```

유니코드 이중 콜론과 화살표도 사용할 수 있다.

```haskell
f ∷ A → B
```

그러므로 첫 번째 하스켈 수업은 이것이다. 이중 콜론은 "타입이 ...이다"라는 뜻이다. 함수 타입은 두 타입 사이에 화살표를 넣어 만든다. 두 함수는 그 사이에 마침표를 넣어 합성한다. 또는 유니코드 원을 써도 된다.

## 합성의 성질

어떤 범주에서든 합성이 반드시 만족해야 하는 매우 중요한 성질이 두 가지 있다.

1. 합성은 결합적이다. 합성할 수 있는 세 사상 f, g, h가 있을 때, 다시 말해 사상들의 객체가 끝과 시작에서 서로 맞물릴 때, 이들을 합성하는 데 괄호가 필요하지 않다. 수학 표기법으로는 다음과 같이 표현한다.

```haskell
h ∘ (g ∘ f) = (h ∘ g) ∘ f = h ∘ g ∘ f
```

하스켈식 의사 코드로는 다음과 같다.

```haskell
f :: A -> B
g :: B -> C
h :: C -> D
h . (g . f) == (h . g) . f == h . g . f
```

("의사" 코드라고 한 것은 함수에 대해서는 동등성이 정의되어 있지 않기 때문이다.)

함수를 다룰 때 결합법칙은 꽤 자명하지만, 다른 범주에서는 그렇게 분명하지 않을 수도 있다.

2. 모든 객체 A에는 합성의 단위가 되는 화살표가 있다. 이 화살표는 객체에서 출발해 다시 그 객체로 돌아오는 고리다. 합성의 단위라는 말은, A에서 시작하거나 A에서 끝나는 어떤 화살표와 각각 합성해도 원래 화살표가 그대로 나온다는 뜻이다. 객체 A의 단위 화살표는 id<sub>A</sub>, 즉 A 위의 항등이라고 부른다. 수학 표기법으로 f가 A에서 B로 간다면 다음이 성립한다.

<pre>
f ∘ id<sub>A</sub> = f
</pre>

그리고 다음도 성립한다.

<pre>
id<sub>B</sub> ∘ f = f
</pre>

함수를 다룰 때 항등 화살표는 받은 인자를 그대로 돌려주는 항등 함수로 구현된다. 이 구현은 모든 타입에 대해 같으므로, 이 함수는 보편적으로 다형적이다. C++에서는 템플릿으로 다음처럼 정의할 수 있다.

```cpp
template<class T> T id(T x) { return x; }
```

물론 C++에서는 무엇을 넘기는지만이 아니라 어떻게 넘기는지도 고려해야 하므로, 어떤 것도 그렇게 단순하지 않다. 값으로 넘길지, 참조로 넘길지, const 참조로 넘길지, 이동으로 넘길지 같은 문제들이 있다.

하스켈에서 항등 함수는 표준 라이브러리, 즉 Prelude의 일부다. 선언과 정의는 다음과 같다.

```haskell
id :: a -> a
id x = x
```

보다시피 하스켈에서 다형 함수는 아주 쉽다. 선언에서 구체 타입을 타입 변수로 바꾸기만 하면 된다. 요령은 이렇다. 구체 타입의 이름은 항상 대문자로 시작하고, 타입 변수의 이름은 소문자로 시작한다. 그러므로 여기서 `a`는 모든 타입을 뜻한다.

하스켈의 함수 정의는 함수 이름 뒤에 형식 매개변수가 오는 형태다. 여기서는 매개변수가 하나, `x`뿐이다. 함수 본문은 등호 뒤에 온다. 이런 간결함은 처음 보는 사람에게 꽤 충격적일 수 있지만, 곧 완벽히 타당하다는 것을 알게 될 것이다. 함수 정의와 함수 호출은 함수형 프로그래밍의 기본 중의 기본이므로 문법이 최소한으로 줄어 있다. 인자 목록을 감싸는 괄호가 없을 뿐 아니라 인자 사이의 쉼표도 없다. 여러 인자를 받는 함수를 정의할 때 나중에 보게 될 것이다.

함수의 본문은 항상 표현식이다. 함수 안에는 문장이 없다. 함수의 결과는 이 표현식이다. 여기서는 그저 `x`다.

이것으로 두 번째 하스켈 수업을 마친다.

항등 조건은 다시 하스켈식 의사 코드로 다음처럼 쓸 수 있다.

```haskell
f . id == f
id . f == f
```

이런 의문이 들 수도 있다. 아무 일도 하지 않는 함수인 항등 함수에 왜 신경을 써야 할까? 하지만 마찬가지로 우리는 왜 숫자 0에 신경을 쓰는가? 0은 없음을 나타내는 기호다. 고대 로마인은 0이 없는 수 체계를 가지고도 훌륭한 도로와 수도교를 건설했고, 그중 일부는 지금까지 남아 있다.

0이나 `id` 같은 중립값은 기호 변수를 다룰 때 매우 유용하다. 로마인이 대수학에 그다지 능하지 않았던 반면, 0의 개념을 알고 있던 아랍인과 페르시아인이 대수학에 능했던 이유도 여기에 있다. 그래서 항등 함수는 고차 함수의 인자로 넘기거나 고차 함수에서 반환할 때 매우 편리해진다. 고차 함수는 함수의 기호적 조작을 가능하게 만든다. 고차 함수는 함수들의 대수학이다.

정리하자. 범주는 객체와 화살표, 즉 사상으로 이루어진다. 화살표는 합성될 수 있고, 그 합성은 결합적이다. 모든 객체에는 합성에서 단위 역할을 하는 항등 화살표가 있다.

## 합성은 프로그래밍의 본질이다

함수형 프로그래머들은 문제에 접근하는 독특한 방식이 있다. 그들은 매우 선문답 같은 질문에서 시작한다. 예를 들어 상호작용 프로그램을 설계할 때 그들은 이렇게 묻는다. 상호작용이란 무엇인가? 콘웨이의 생명 게임을 구현할 때라면 아마도 생명의 의미를 곰곰이 생각할 것이다. 같은 정신으로 나는 이렇게 묻겠다. 프로그래밍이란 무엇인가? 가장 기본적인 수준에서 프로그래밍은 컴퓨터에게 무엇을 해야 하는지 말해 주는 일이다. "메모리 주소 x의 내용을 가져와 레지스터 EAX의 내용에 더하라." 하지만 어셈블리어로 프로그래밍할 때조차 우리가 컴퓨터에 주는 명령은 더 의미 있는 무언가의 표현이다. 우리는 사소하지 않은 문제를 풀고 있다. 사소한 문제라면 컴퓨터의 도움이 필요 없을 것이다. 그렇다면 우리는 문제를 어떻게 푸는가? 큰 문제를 작은 문제들로 분해한다. 작은 문제들이 여전히 너무 크다면 더 잘게 분해하고, 그렇게 계속한다. 마침내 우리는 모든 작은 문제를 푸는 코드를 작성한다. 그리고 그다음 프로그래밍의 본질이 온다. 그 코드 조각들을 합성해 더 큰 문제의 해답을 만든다. 조각들을 다시 맞출 수 없다면 분해는 아무 의미가 없을 것이다.

이런 계층적 분해와 재합성 과정은 컴퓨터가 우리에게 강요한 것이 아니다. 그것은 인간 정신의 한계를 반영한다. 우리의 뇌는 한 번에 적은 수의 개념만 다룰 수 있다. 심리학에서 가장 많이 인용되는 논문 중 하나인 [마법의 숫자 7, 더하거나 빼기 2](https://en.wikipedia.org/wiki/The_Magical_Number_Seven,_Plus_or_Minus_Two)는 우리가 마음속에 정보의 "덩어리"를 7±2개 정도만 유지할 수 있다고 가정했다. 인간의 단기 기억에 대한 세부적인 이해는 바뀌고 있을지 몰라도, 그것이 제한되어 있다는 사실은 분명하다. 핵심은 우리가 객체의 수프나 코드의 스파게티를 다룰 수 없다는 점이다. 구조화된 프로그램이 보기 좋기 때문에 구조가 필요한 것이 아니다. 그렇지 않으면 우리의 뇌가 효율적으로 처리할 수 없기 때문에 구조가 필요하다. 우리는 어떤 코드를 우아하다거나 아름답다고 자주 말하지만, 실제로 뜻하는 바는 제한된 인간 정신이 처리하기 쉽다는 것이다. 우아한 코드는 우리의 정신적 소화 기관이 받아들이기에 딱 맞는 크기와 딱 맞는 수의 덩어리를 만든다.

그렇다면 프로그램을 합성하기에 알맞은 덩어리는 무엇일까? 그 표면적은 부피보다 느리게 증가해야 한다. 나는 이 비유를 좋아한다. 기하학적 물체의 표면적은 크기의 제곱에 비례해 자라고, 부피는 크기의 세제곱에 비례해 자란다는 직관 때문이다. 표면적은 덩어리들을 합성하기 위해 필요한 정보다. 부피는 그 덩어리들을 구현하기 위해 필요한 정보다. 핵심은 덩어리 하나가 구현되고 나면 그 구현의 세부 사항은 잊고, 그것이 다른 덩어리들과 어떻게 상호작용하는지에 집중할 수 있다는 것이다. 객체 지향 프로그래밍에서 표면은 객체의 클래스 선언 또는 추상 인터페이스다. 함수형 프로그래밍에서는 함수의 선언이다. 조금 단순화하고 있지만 요지는 그렇다.

범주론은 객체의 내부를 들여다보는 일을 적극적으로 discourages한다는 점에서 극단적이다. 범주론에서 객체는 추상적이고 흐릿한 존재다. 객체에 대해 알 수 있는 것은 그것이 다른 객체와 어떤 관계를 맺는가, 즉 화살표를 통해 어떻게 연결되는가뿐이다. 인터넷 검색 엔진이 들어오는 링크와 나가는 링크를 분석해 웹사이트의 순위를 매기는 방식도 이와 비슷하다. 속임수를 쓰는 경우는 제외하고 말이다. 객체 지향 프로그래밍에서 이상화된 객체는 추상 인터페이스를 통해서만 보인다. 순수한 표면만 있고 부피는 없다. 메서드는 화살표의 역할을 한다. 객체를 다른 객체와 어떻게 합성할지 이해하기 위해 그 객체의 구현 안을 파헤쳐야 하는 순간, 당신은 프로그래밍 패러다임의 장점을 잃어버린 것이다.

### 연습문제

1. 좋아하는 언어로 항등 함수를 가능한 한 잘 구현해 보라. 좋아하는 언어가 하스켈이라면 두 번째로 좋아하는 언어를 사용하라.

2. 좋아하는 언어로 함수 합성을 구현해 보라. 이 함수는 두 함수를 인자로 받아 그 둘의 합성인 함수를 반환한다.

3. 당신의 합성 함수가 항등성을 만족하는지 시험해 보는 프로그램을 작성하라.

4. 월드 와이드 웹은 어떤 의미에서 범주인가? 링크는 사상인가?

5. 페이스북은 사람을 객체로, 친구 관계를 사상으로 하는 범주인가?

6. 방향 그래프는 언제 범주가 되는가?
