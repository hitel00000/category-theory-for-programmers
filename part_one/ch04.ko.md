# 클라이슬리 범주

## 로그의 합성

우리는 타입과 순수 함수를 범주로 모델링하는 방법을 보았다. 또한 부수 효과, 또는 순수하지 않은 함수를 범주론으로 모델링하는 방법이 있다고도 말했다. 그런 예 하나를 살펴보자. 실행 과정을 로그로 남기거나 추적하는 함수다. 명령형 언어에서는 아마 다음처럼 어떤 전역 상태를 변경해서 구현할 법한 일이다.

```cpp
string logger;

bool negate(bool b) {
     logger += "Not so! ";
     return !b;
}
```

이 함수가 순수 함수가 아니라는 것은 알 수 있다. 메모화한 버전은 로그를 만들어 내지 못할 것이기 때문이다. 이 함수에는 부수 효과가 있다.

현대 프로그래밍에서는 전역 가변 상태를 가능한 한 피하려고 한다. 동시성의 복잡함만 생각해도 그렇다. 그리고 이런 코드를 라이브러리에 넣지는 않을 것이다.

다행히 이 함수를 순수하게 만들 수 있다. 로그를 명시적으로 입력과 출력으로 넘기면 된다. 문자열 인자를 하나 추가하고, 일반적인 출력과 갱신된 로그가 담긴 문자열을 쌍으로 묶어 반환해 보자.

```cpp
pair<bool, string> negate(bool b, string logger) {
     return make_pair(!b, logger + "Not so! ");
}
```

이 함수는 순수하다. 부수 효과가 없고, 같은 인자로 호출될 때마다 같은 쌍을 반환하며, 필요하다면 메모화할 수도 있다. 다만 로그가 누적되는 성질을 고려하면, 어떤 호출에 이르는 가능한 모든 이력을 메모화해야 할 것이다. 다음 호출에 대한 메모 항목이 따로 있어야 한다.

```cpp
negate(true, "It was the best of times. ");
```

그리고 다음도 따로 있어야 한다.

```cpp
negate(true, "It was the worst of times. ");
```

이런 식이다.

라이브러리 함수의 인터페이스로도 그다지 좋지 않다. 호출자는 반환 타입 안의 문자열을 무시해도 되므로 큰 부담은 아니지만, 입력으로 문자열을 반드시 넘겨야 하므로 불편할 수 있다.

같은 일을 덜 침투적인 방식으로 할 수 있을까? 관심사를 분리할 방법이 있을까? 이 단순한 예에서 `negate` 함수의 주된 목적은 불리언 하나를 다른 불리언으로 바꾸는 것이다. 로깅은 부차적이다. 물론 기록되는 메시지는 함수에 따라 다르지만, 메시지들을 하나의 연속된 로그로 모으는 일은 별개의 관심사다. 우리는 여전히 함수가 문자열을 만들어 내기를 원하지만, 로그 전체를 만들어 내는 부담은 덜어 주고 싶다. 그래서 타협안은 다음과 같다.

```cpp
pair<bool, string> negate(bool b) {
     return make_pair(!b, "Not so! ");
}
```

아이디어는 로그를 함수 호출 사이에서 모으겠다는 것이다.

이것이 어떻게 가능한지 보기 위해 조금 더 현실적인 예로 넘어가 보자. 소문자를 대문자로 바꾸는, 문자열에서 문자열로 가는 함수가 하나 있다.

```cpp
string toUpper(string s) {
    string result;
    int (*toupperp)(int) = &toupper; // toupper is overloaded
    transform(begin(s), end(s), back_inserter(result), toupperp);
    return result;
}
```

그리고 문자열을 공백 경계에서 잘라 문자열 벡터로 나누는 또 다른 함수가 있다.

```cpp
vector<string> toWords(string s) {
    return words(s);
}
```

실제 작업은 보조 함수 `words`에서 이루어진다.

```cpp
vector<string> words(string s) {
    vector<string> result{""};
    for (auto i = begin(s); i != end(s); ++i)
    {
        if (isspace(*i))
            result.push_back("");
        else
            result.back() += *i;
    }
    return result;
}
```

우리는 `toUpper`와 `toWords`를 수정해, 일반 반환값 위에 메시지 문자열을 얹어 함께 돌려주고 싶다.

![](images/piggyback.jpg)

이 함수들의 반환값을 "장식"하자. 임의의 타입 `A`의 값을 첫 번째 구성 요소로, 문자열을 두 번째 구성 요소로 갖는 쌍을 감싸는 템플릿 `Writer`를 정의해 일반적인 방식으로 해 보자.

```cpp
template<class A>
using Writer = pair<A, string>;
```

장식된 함수들은 다음과 같다.

```cpp
Writer<string> toUpper(string s) {
    string result;
    int (*toupperp)(int) = &toupper;
    transform(begin(s), end(s), back_inserter(result), toupperp);
    return make_pair(result, "toUpper ");
}

Writer<vector<string>> toWords(string s) {
    return make_pair(words(s), "toWords ");
}
```

이 두 함수를 합성해, 문자열을 대문자로 바꾸고 단어로 나누면서 동시에 그 동작들의 로그를 만들어 내는 또 다른 장식된 함수를 만들고 싶다. 다음처럼 할 수 있다.

```cpp
Writer<vector<string>> process(string s) {
    auto p1 = toUpper(s);
    auto p2 = toWords(p1.first);
    return make_pair(p2.first, p1.second + p2.second);
}
```

목표를 달성했다. 로그를 모으는 일은 더 이상 개별 함수의 관심사가 아니다. 함수들은 자기 메시지를 만들고, 그 메시지들은 외부에서 더 큰 로그로 연결된다.

이제 이런 방식으로 작성된 전체 프로그램을 상상해 보라. 반복적이고 오류가 나기 쉬운 코드의 악몽이다. 하지만 우리는 프로그래머다. 반복 코드를 다루는 법을 안다. 추상화하면 된다. 다만 이것은 흔한 추상화가 아니다. 함수 합성 자체를 추상화해야 한다. 그러나 합성은 범주론의 본질이므로, 코드를 더 쓰기 전에 범주론적 관점에서 문제를 분석해 보자.

## Writer 범주

여러 함수의 반환 타입을 장식해 추가 기능을 얹는 아이디어는 매우 유익한 것으로 드러난다. 앞으로 더 많은 예를 보게 될 것이다. 출발점은 타입과 함수의 일반적인 범주다. 객체는 타입 그대로 두되, 사상을 장식된 함수로 재정의하겠다.

예를 들어 `int`에서 `bool`로 가는 함수 `isEven`을 장식하고 싶다고 하자. 우리는 이 함수를 장식된 함수로 표현되는 사상으로 바꾼다. 중요한 점은 장식된 함수가 쌍을 반환하더라도, 이 사상은 여전히 객체 `int`와 `bool` 사이의 화살표로 간주된다는 것이다.

```cpp
pair<bool, string> isEven(int n) {
     return make_pair(n % 2 == 0, "isEven ");
}
```

범주의 법칙에 따르면, 이 사상은 객체 `bool`에서 무엇인가로 가는 다른 사상과 합성될 수 있어야 한다. 특히 앞서 본 `negate`와 합성할 수 있어야 한다.

```cpp
pair<bool, string> negate(bool b) {
     return make_pair(!b, "Not so! ");
}
```

입출력 타입이 맞지 않으므로, 이 두 사상을 일반 함수처럼 합성할 수는 없다. 그 합성은 다음과 비슷해야 한다.

```cpp
pair<bool, string> isOdd(int n) {
    pair<bool, string> p1 = isEven(n);
    pair<bool, string> p2 = negate(p1.first);
    return make_pair(p2.first, p1.second + p2.second);
}
```

따라서 우리가 만들고 있는 새 범주에서 두 사상을 합성하는 조리법은 다음과 같다.

1. 첫 번째 사상에 대응하는 장식된 함수를 실행한다.

2. 결과 쌍의 첫 번째 구성 요소를 꺼내 두 번째 사상에 대응하는 장식된 함수에 넘긴다.

3. 첫 번째 결과의 두 번째 구성 요소, 즉 문자열과 두 번째 결과의 두 번째 구성 요소, 즉 문자열을 연결한다.

4. 최종 결과의 첫 번째 구성 요소와 연결된 문자열을 합쳐 새 쌍을 반환한다.

이 합성을 C++에서 고차 함수로 추상화하려면, 범주의 세 객체에 대응하는 세 타입으로 매개변수화된 템플릿을 사용해야 한다. 이 템플릿은 우리의 규칙에 따라 합성 가능한 두 장식된 함수를 받아 세 번째 장식된 함수를 반환해야 한다.

```cpp
template<class A, class B, class C>
function<Writer<C>(A)> compose(function<Writer<B>(A)> m1, 
                               function<Writer<C>(B)> m2)
{
    return [m1, m2](A x) {
        auto p1 = m1(x);
        auto p2 = m2(p1.first);
        return make_pair(p2.first, p1.second + p2.second);
    };
}
```

이제 앞의 예로 돌아가 이 새 템플릿을 사용해 `toUpper`와 `toWords`의 합성을 구현할 수 있다.

```cpp
Writer<vector<string>> process(string s) {
   return compose<string, string, vector<string>>(toUpper, toWords)(s);
}
```

아직도 `compose` 템플릿에 타입을 넘기는 잡음이 많다. C++14를 준수하고 반환 타입 추론이 있는 일반화 람다 함수를 지원하는 컴파일러가 있다면 이를 피할 수 있다. 이 코드는 Eric Niebler가 제공했다.

```cpp
auto const compose = [](auto m1, auto m2) {
    return [m1, m2](auto x) {
        auto p1 = m1(x);
        auto p2 = m2(p1.first);
        return make_pair(p2.first, p1.second + p2.second);
    };
};
```

이 새 정의에서는 `process`의 구현이 다음처럼 단순해진다.

```cpp
Writer<vector<string>> process(string s){
   return compose(toUpper, toWords)(s);
}
```

하지만 아직 끝나지 않았다. 새 범주에서 합성을 정의했지만, 항등 사상은 무엇인가? 이것은 일반적인 항등 함수가 아니다. 타입 A에서 다시 타입 A로 가는 사상이어야 하므로, 다음 형태의 장식된 함수여야 한다.

```cpp
Writer<A> identity(A);
```

이 함수들은 합성에 대해 단위처럼 동작해야 한다. 우리의 합성 정의를 보면, 항등 사상은 인자를 변경하지 않고 그대로 전달하면서 로그에는 빈 문자열만 더해야 한다는 것을 알 수 있다.

```cpp
template<class A>
Writer<A> identity(A x) {
    return make_pair(x, "");
}
```

방금 정의한 범주가 실제로 정당한 범주라는 것은 쉽게 납득할 수 있다. 특히 우리의 합성은 자명하게 결합적이다. 각 쌍의 첫 번째 구성 요소에 무슨 일이 일어나는지 따라가 보면, 그것은 결합적인 일반 함수 합성일 뿐이다. 두 번째 구성 요소들은 연결되고 있으며, 연결 역시 결합적이다.

예리한 독자라면 이 구성을 문자열 모노이드뿐 아니라 임의의 모노이드로 쉽게 일반화할 수 있음을 알아차릴 수 있다. `compose` 안에서는 `+` 대신 `mappend`를, `identity` 안에서는 `""` 대신 `mempty`를 사용하면 된다. 로그를 문자열로 제한할 이유는 전혀 없다. 좋은 라이브러리 작성자라면 라이브러리가 동작하는 데 필요한 최소한의 제약을 식별할 수 있어야 한다. 여기서 로깅 라이브러리의 유일한 요구 사항은 로그가 모노이드 성질을 가져야 한다는 것이다.

## 하스켈의 Writer

하스켈에서 같은 일은 조금 더 간결하고, 컴파일러의 도움도 훨씬 많이 받을 수 있다. `Writer` 타입을 정의하는 것부터 시작하자.

```haskell
type Writer a = (a, String)
```

여기서는 타입 별칭을 정의하고 있을 뿐이다. C++의 `typedef` 또는 `using`에 해당한다. `Writer` 타입은 타입 변수 `a`로 매개변수화되며, `a`와 `String`의 쌍과 동등하다. 쌍의 문법은 최소한이다. 괄호 안에 두 항목을 쉼표로 구분해 넣으면 된다.

우리의 사상은 임의의 타입에서 어떤 `Writer` 타입으로 가는 함수다.

```haskell
a -> Writer b
```

합성은 재미있는 중위 연산자로 선언하겠다. 때때로 "fish"라고 부르는 연산자다.

```haskell
(>=>) :: (a -> Writer b) -> (b -> Writer c) -> (a -> Writer c)
```

이것은 두 인자의 함수이며, 각 인자는 그 자체로 함수이고, 결과도 함수다. 첫 번째 인자는 `(a->Writer b)` 타입이고, 두 번째 인자는 `(b->Writer c)` 타입이며, 결과는 `(a->Writer c)`다.

이 중위 연산자의 정의는 다음과 같다. 두 인자 `m1`과 `m2`가 fish 기호의 양쪽에 나타난다.

```haskell
m1 >=> m2 = \x -> 
    let (y, s1) = m1 x
        (z, s2) = m2 y
    in (z, s1 ++ s2)
```

결과는 하나의 인자 `x`를 받는 람다 함수다. 람다는 백슬래시로 쓴다. 다리 하나가 잘린 그리스 문자 람다라고 생각하면 된다.

`let` 표현식은 보조 변수를 선언하게 해 준다. 여기서는 `m1` 호출 결과를 `(y, s1)`이라는 변수 쌍에 패턴 매칭하고, 첫 번째 패턴에서 얻은 인자 `y`로 `m2`를 호출한 결과를 `(z, s2)`에 매칭한다.

하스켈에서는 C++에서처럼 접근자를 사용하는 대신 쌍을 패턴 매칭하는 일이 흔하다. 그 외에는 두 구현 사이에 꽤 직접적인 대응이 있다.

`let` 표현식 전체의 값은 `in` 절에서 지정된다. 여기서는 첫 번째 구성 요소가 `z`이고 두 번째 구성 요소가 두 문자열 `s1++s2`의 연결인 쌍이다.

우리 범주의 항등 사상도 정의하겠다. 하지만 훨씬 나중에 분명해질 이유 때문에 이것을 `return`이라고 부르겠다.

```haskell
return :: a -> Writer a
return x = (x, "")
```

완전성을 위해 장식된 함수 `upCase`와 `toWords`의 하스켈 버전도 보자.

```haskell
upCase :: String -> Writer String
upCase s = (map toUpper s, "upCase ")
```

```haskell
toWords :: String -> Writer [String]
toWords s = (words s, "toWords ")
```

함수 `map`은 C++의 `transform`에 대응한다. 문자 함수 `toUpper`를 문자열 `s`에 적용한다. 보조 함수 `words`는 표준 Prelude 라이브러리에 정의되어 있다.

마지막으로 두 함수의 합성은 fish 연산자의 도움으로 이루어진다.

```haskell
process :: String -> Writer [String]
process = upCase >=> toWords
```

## 클라이슬리 범주

내가 이 범주를 즉석에서 발명한 것이 아니라는 점은 짐작했을지도 모른다. 이것은 이른바 클라이슬리 범주의 예다. 모나드에 기반한 범주다. 우리는 아직 모나드를 논의할 준비가 되어 있지 않지만, 모나드가 무엇을 할 수 있는지 맛보기로 보여 주고 싶었다. 우리의 제한된 목적에서 클라이슬리 범주는 기반 프로그래밍 언어의 타입들을 객체로 갖는다. 타입 A에서 타입 B로 가는 사상은 A에서 특정한 장식을 사용해 B로부터 파생된 타입으로 가는 함수다. 각 클라이슬리 범주는 그런 사상들을 합성하는 자기만의 방식과, 그 합성에 대한 항등 사상을 정의한다. 나중에 "장식"이라는 부정확한 말이 범주의 endofunctor 개념에 대응한다는 것을 보게 될 것이다.

이 글에서 범주의 기반으로 사용한 특정 모나드는 writer monad라고 부르며, 함수 실행을 로깅하거나 추적하는 데 사용된다. 또한 순수 계산 안에 효과를 포함시키는 더 일반적인 메커니즘의 예이기도 하다. 앞서 우리는 프로그래밍 언어의 타입과 함수를 집합의 범주 안에서 모델링할 수 있음을 보았다. 늘 그렇듯 bottom은 무시했다. 여기서는 이 모델을 약간 다른 범주로 확장했다. 사상이 장식된 함수로 표현되고, 합성은 한 함수의 출력을 다른 함수의 입력으로 넘기는 일보다 더 많은 일을 하는 범주다. 우리에게는 가지고 놀 수 있는 자유도가 하나 더 생겼다. 합성 자체다. 바로 이 자유도가 명령형 언어에서 전통적으로 부수 효과를 사용해 구현되는 프로그램에 단순한 표시적 의미론을 줄 수 있게 해 준다는 사실이 드러난다.

## 연습문제

인자의 가능한 모든 값에 대해 정의되어 있지 않은 함수를 부분 함수라고 부른다. 이것은 수학적 의미에서는 진짜 함수가 아니므로 표준적인 범주론 틀에는 맞지 않는다. 하지만 장식된 타입 `optional`을 반환하는 함수로 표현할 수 있다.

```cpp
template<class A> class optional {
    bool _isValid;
    A    _value;
public:
    optional()    : _isValid(false) {}
    optional(A v) : _isValid(true), _value(v) {}
    bool isValid() const { return _isValid; }
    A value() const { return _value; }
};
```

예를 들어 장식된 함수 `safe_root`의 구현은 다음과 같다.

```cpp
optional<double> safe_root(double x) {
    if (x >= 0) return optional<double>{sqrt(x)};
    else return optional<double>{};
}
```

연습문제는 다음과 같다.

1. 부분 함수에 대한 클라이슬리 범주를 구성하라. 합성과 항등을 정의하라.

2. 인자가 0이 아닐 때 유효한 역수를 반환하는 장식된 함수 `safe_reciprocal`을 구현하라.

3. `safe_root`와 `safe_reciprocal`을 합성해, 가능할 때마다 `sqrt(1/x)`를 계산하는 `safe_root_reciprocal`을 구현하라.
